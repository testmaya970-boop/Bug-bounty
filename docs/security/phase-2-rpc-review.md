## Finding: the three RLS helper functions were directly callable via the Data API

**Status: fixed in this revision of the migration.**

### What was wrong

`is_org_member`, `has_org_role`, and `shares_organization_with` were created as `public.is_org_member(...)` etc. — in the `public` schema, which `supabase/config.toml`'s `[api] schemas = ["public", "graphql_public"]` exposes as callable RPC endpoints. Each had `revoke all ... from public; grant execute ... to authenticated;`, which is necessary hygiene (blocks `anon`) but not sufficient: any **authenticated** Sentinel user — including one who belongs to zero organizations — could call `supabase.rpc('is_org_member', { target_org_id: '<any-uuid>' })` directly and get back a real answer, because the function is `SECURITY DEFINER` and therefore reads `organization_members` bypassing that table's own RLS.

### Exact vulnerable surface (answering the nine questions in order)

1. **Schema**: all three were created in `public`.
2. **Exposed through the Data API?** Yes — `public` is in `supabase/config.toml`'s `schemas` list, so PostgREST routes `/rest/v1/rpc/is_org_member`, `/rest/v1/rpc/has_org_role`, `/rest/v1/rpc/shares_organization_with` to them.
3. **Can an authenticated or anonymous caller invoke it directly?** `anon` could not (no grant). Any **authenticated** user could, for arbitrary arguments — this is the actual gap.
4. **Attacker-controlled arguments?** Yes — `target_org_id`, `allowed_roles`, `target_user_id` are all caller-supplied with no ownership check on the caller's side before the function runs.
5. **Privileges the function executes with?** The function owner's (the role that ran the migration — `postgres`/`supabase_admin` in practice), which bypasses `organization_members`' RLS for the function's internal `SELECT`. This is *necessary* for the function to do its job as an RLS-recursion-breaking helper; it is *not* something that should be reachable as a standalone API call.
6. **Can it reveal membership/organization information?** Yes. `is_org_member(org_id)` answers "does this organization currently have any active member?" for an org the caller may not belong to. `has_org_role(org_id, roles)` answers "does this organization have an active member with one of these roles?" — usable to probe, e.g., "does org X currently have zero owners" as a precursor to a social-engineering attempt. `shares_organization_with(user_id)` answers "do I share an active organization with this other user?" for an arbitrary `user_id`, without the caller needing to already know which organization.
7. **Can it mutate anything?** No — all three are `stable`, read-only, return `boolean`. This bounds the finding to information disclosure, not privilege escalation or data corruption.
8. **Do the function's privileges exceed what the calling role should have?** Yes — an ordinary authenticated user's own RLS-scoped view of `organization_members` only ever shows organizations they belong to; calling these functions directly grants a narrow but real query oracle into *other* organizations' membership existence, which their own RLS-scoped `SELECT` privileges would never allow.
9. **Were EXECUTE privileges granted/revoked appropriately?** Partially — the `revoke from public` / `grant to authenticated` pattern correctly blocks anonymous access and matches Supabase's own documented baseline hygiene for `SECURITY DEFINER` functions, but grants alone cannot close this specific gap: `authenticated` genuinely needs `EXECUTE` for RLS policy evaluation to succeed at all (the role evaluating a policy must be able to invoke every function the active policy expression references). Revoking `EXECUTE` from `authenticated` would have broken every RLS policy on `organization_members`, `users`, `organization_invitations`, and `audit_logs` that references these helpers.

**Practical exploitability**: bounded by organization/user IDs being UUIDv4 (not enumerable or guessable) — an attacker needs to already have a valid ID from some other source (e.g., observed in a URL, a future feature that leaks one, or a compromised low-privilege account). This is not a "browse all organizations" vulnerability. It *is* a real violation of least privilege and of `SECURITY.md`'s "private program existence must not be disclosed to unauthorized users" principle (organizations are the closest analog that exists yet), and it's exactly the class of function-exposure risk Supabase's own security documentation calls out by name.

### The fix

Moved all three functions to a new `private` schema (`create schema if not exists private`), which is **not** listed in `supabase/config.toml`'s `[api] schemas` and therefore is never routed to by PostgREST, regardless of any `GRANT`. `authenticated` still has `USAGE` on `private` and `EXECUTE` on the three functions — required for RLS policy evaluation — but that grant no longer creates a public HTTP endpoint, because schema exposure (not the grant) is what PostgREST's routing is gated on. Every internal reference (4 RLS policies, `invite_organization_member`, `cancel_organization_invitation`) was updated from `public.<fn>` to `private.<fn>`. `supabase/config.toml` now carries an explicit comment warning that `private` must never be added to the exposed-schemas list, and the same warning is in the migration file itself, next to the `create schema` statement.

This is the intended architecture stated in the task:

```text
client → PostgREST → public API (mutation RPCs, intentionally exposed)
                          ↓ (internally, not over HTTP)
                    private SECURITY DEFINER helper → RLS evaluation
```

The seven mutation RPCs below remain in `public` **by design** — they are the actual application API surface, and each independently re-derives and re-checks the caller's authorization from `auth.uid()` before doing anything, so their exposure is not the finding.

## Mutation RPC review

All seven share these properties, stated once instead of seven times: **caller identity source** is always `auth.uid()`, re-derived inside the function, never a parameter — no function accepts an actor/user id from the client. **Transaction boundary** is the function call itself — a single `plpgsql` function invocation is one Postgres transaction, so the mutation and its audit-log insert are atomic by construction. **SECURITY DEFINER/INVOKER**: all `SECURITY DEFINER`. **search_path**: all `''`, every reference schema-qualified. **EXECUTE privileges**: `revoke all ... from public`, then `grant execute ... to authenticated` — intentionally callable by any authenticated user; the function body is the authorization boundary, not the grant. **Exposed schema**: `public` (intentional — this is the app's API surface).

This was a deliberate scope decision in the original Phase 2 build (not adding validation for a scenario the spec didn't require) — flagged here for visibility, not treated as part of this session's security finding.

**Why `list_my_pending_invitations` needs its own `SECURITY DEFINER` function rather than a new RLS policy**: an invitee has no other RLS-permitted path to read the *organization's name* before they're a member (`organizations`' own SELECT policy requires active membership, which by definition an invitee doesn't have). **Two real bugs found during live verification of this migration, both fixed in the same migration file** (not a separate patch, since neither had ever executed anywhere): (1) `create_organization`'s idempotency-key parameter shared its exact name with the `organizations.idempotency_key` column, making every bare reference to it inside the function body ambiguous to Postgres (`42702`) — fixed by prefixing the parameter (`p_idempotency_key`), the standard plpgsql idiom for this class of bug. (2) `list_my_pending_invitations`'s `RETURNS TABLE(id uuid, ...)` made `id` an output-parameter-like variable in scope across the *entire* function body — an unrelated, earlier query (`select email into actor_email from public.users where id = actor`) collided with it the same way, fixed by qualifying that reference. Neither bug was security-relevant (both were fail-closed errors, not silent bypasses), but neither was catchable by source review alone — both were found only by actually running the functions.

## Program Foundation RPC review (202608260004)

| Function | Schema | Authorization check | Client-supplied identity? | Transaction boundary | Audit event |
|---|---|---|---|---|---|
| `create_program(target_org_id, program_name, p_idempotency_key)` | `public` | `private.has_org_role(target_org_id, ['owner','security_admin'])` — the same allowed-role set `services/authorization.ts`'s `canCreateProgram` expresses client-side (see `docs/decisions/0004-program-authorization.md`) | None — `created_by`/manager/role/status are never parameters, only derived from `auth.uid()` or hardcoded (`status` is always inserted as `'draft'`) | Single function call: authorization check, name validation, idempotent-replay check, program insert (with the same unique-constraint-triggered race-safe replay branch `create_organization` uses), `program_members` manager-row insert, and audit insert are all one transaction | `program.created`, actor = creator, entity = new program id |
| `private.is_program_member(target_program_id)` | `private` | N/A (read-only helper, not directly callable — see below) | N/A | Read-only | None |

**Why `create_program` needs an authorization check `create_organization` does not**: organization creation has no parent resource to be authorized against (any authenticated user may create one); program creation does — a program always belongs to an existing organization, and `DOMAIN.md`'s "Organization membership" section requires program-level access to be a distinct, explicitly-granted concept, never inferred from the caller merely supplying a plausible-looking `target_org_id`. A user from Organization A supplying Organization B's id receives the identical `FORBIDDEN` error whether B exists and they're not a member, or B does not exist at all — confirmed live (see below) — so no existence oracle is created either way.

**Why `private.is_program_member` follows the exact `private.is_org_member` pattern**: same rationale as the original finding at the top of this document — a `SECURITY DEFINER` membership-check helper placed in `public` would be directly callable over the Data API as an arbitrary-program-id membership oracle, bypassing `program_members`' own RLS. It is defined in `private` (not exposed by `supabase/config.toml`), `plpgsql` (never planner-inlined), `stable`, `search_path = ''`, and `EXECUTE` is granted to `authenticated` only (required for RLS evaluation), never `anon` or `PUBLIC`.

**No bugs found in this migration.** Unlike `202608260003`, this migration reused an already-fixed pattern throughout — the renamed `p_idempotency_key` parameter (never re-introducing the column-name collision), and a single-row `returns public.programs` (never a `RETURNS TABLE(...)` whose column names could collide with an internal variable, the mechanism behind the second organization-creation bug). Both classes of bug this file could have repeated were structurally avoided rather than re-found live.

## Program Scope & Asset Foundation RPC review (202608260005)

| Function | Schema | Authorization check | Client-supplied identity? | Transaction boundary | Audit event |
|---|---|---|---|---|---|
| `private.canonicalize_scope_target(asset_type, target_input)` | `private` | N/A -- pure computation, no table access, no elevated privilege needed | N/A | Read-only | None |
| `add_scope_entry(target_program_id, asset_type, target_input, scope_state, description)` | `public` | `private.has_org_role(program.organization_id, ['owner','security_admin'])` or `private.is_program_member(program.id)`; additionally requires `program.status = 'draft'` | None — `created_by` is never a parameter; the canonical `target`/`display_target`/`target_cidr`/`url_origin`/`url_path` are computed server-side, never accepted from the client | Single function call: authorization + lifecycle check, canonicalization, insert (with a `unique_violation`-to-`DUPLICATE_TARGET` remap), and audit insert are all one transaction | `scope.asset_added` |
| `update_scope_entry(entry_id, scope_state, description)` | `public` | Same two-path check, resolved from the entry's own program, not a client-supplied org/program id; same `draft`-only lifecycle check | `entry_id` only; the target/asset_type are immutable and cannot be changed through this function at all | Single function call | `scope.asset_updated` (records previous and new `scope_state`) |
| `remove_scope_entry(entry_id)` | `public` | Same two-path check; same `draft`-only lifecycle check | `entry_id` only | Single function call; soft-delete (`status='removed'`), never a physical `DELETE` | `scope.asset_removed` |
| `evaluate_program_scope(target_program_id, asset_type, target_input)` | `public` | Same two-path check as every other scope operation — **not** a researcher-facing endpoint; a caller with no organization/program relationship to the program is rejected identically to every other scope operation | None beyond the target being evaluated | Read-only | None (a read) |

**Why every scope-mutation RPC re-resolves the program's `organization_id` from the database, never from a parameter**: `add_scope_entry` takes `target_program_id`, looks up the real `programs` row, and authorizes against *that* row's `organization_id` — a client cannot claim a program belongs to an organization it does not actually belong to. `update_scope_entry`/`remove_scope_entry` go one step further and don't even accept a program or organization id at all; they resolve everything from the located `program_scope_entries` row itself (`entry_id` → its `program_id` → that program's real `organization_id`), so there is no parameter combination that could point authorization at the wrong tenant.

**Why IP/CIDR containment uses Postgres's native `>>=` operator, not string matching**: `program_scope_entries.target_cidr` is a real `cidr` column; `evaluate_program_scope`'s IP/CIDR branch is `e.target_cidr >>= canon.cidr_value`, native network-address containment, not a hand-rolled prefix/string comparison that could get boundary cases wrong. `private.canonicalize_scope_target`'s own `raw::cidr` cast additionally rejects any input whose host bits are set beyond its declared prefix (Postgres's own `cidr` semantics, not application logic) — confirmed live below.

**Why domain-wildcard matching cannot be fooled by `evil-example.com`**: the match condition is `left(e.target, 2) = '*.' and canon.canonical like ('%.' || substr(e.target, 3))` — a `LIKE '%.<suffix>'` pattern requires a literal `.` immediately before the suffix, which `evil-example.com` does not have before `example.com` (it has `-`). This is a real DNS-label-boundary check, not a `string.endsWith()`-style substring test that a hyphenated lookalike domain could defeat.

**No bugs found in this migration**, despite being the most complex one in this codebase to date (three asset types, each with its own canonicalization and matching semantics). The full canonicalization/validation boundary-case matrix, the full precedence/matching matrix (domain wildcard nesting and explicit-exclusion override, URL path-boundary matching, IP/CIDR containment with a more-specific exclusion), duplicate detection (sequential, case/trailing-dot-equivalent, and genuinely concurrent), the lifecycle lock, and the full authorization matrix (owner/triager/cross-tenant/anonymous) were all run live against a real local Postgres instance before this was considered done — see "DATABASE VERIFIED" below.

**Why there is no generic `update_report_status(status)` RPC**: the task's own framing — "a generic status RPC becomes an authorization bypass waiting to happen" — is architecturally enforced here, not just followed by convention. Each of the eight transition functions hardcodes its own target status as a string literal in its own `update` statement; there is no code path anywhere in this migration where a `report_status` value flows from a function parameter into a `set status = ...` clause. `private.report_status_transitions` (the data-driven table) and `private.is_valid_report_transition` exist so the *validation* rule lives in one place, not so the *target status* can be parameterized — those are deliberately different design decisions.

**Why `private.lock_and_authorize_report_for_triage` takes `select ... for update`, unlike every other authorize-and-locate helper in this schema**: every earlier authorization helper (`is_program_member`, `is_researcher_authorized_for_program`, `match_program_scope`) is read-only, because nothing upstream of it could conflict with a concurrent identical call. Report triage is different: two managers can genuinely race to transition the same report, and without a row lock, both could read the same `status`, both pass `is_valid_report_transition`, and both write — a classic lost-update / impossible-combined-state bug. The `for update` lock forces the loser to block until the winner's transaction commits, then re-read the now-current `status` and correctly fail the transition check. See "Genuine concurrent conflicting transitions" below for the live proof.

**Why `respond_to_information_request` does not use `private.lock_and_authorize_report_for_triage`**: that helper's authorization check is manager-only (`has_org_role` or `is_program_member`) — it would incorrectly reject the submitting researcher, or worse, incorrectly authorize a *different* researcher who happens to also be a program manager elsewhere. Responding to an information request is a researcher action on their own report, the same authorization shape `submit_report` already established, so it repeats that shape rather than reusing the manager helper.

**One real bug found live and fixed in this migration**: every `INVALID_TRANSITION` rejection (and the `INVALID_REASON`/`INVALID_RESOLUTION`/`INVALID_RESPONSE`/`INVALID_DUPLICATE_TARGET` validation errors) originally used `errcode = '55000'` (`object_not_in_prerequisite_state`), copying the pattern the scope-foundation migration's `SCOPE_LOCKED` and the report-foundation migration's `SUBMISSIONS_CLOSED` already used. Live HTTP verification showed the JSON error body was correct but the **HTTP status was `500`**, not the expected `4xx` — `55000` is not in PostgREST's default SQLSTATE→HTTP mapping table and falls through to its generic-error `500` default, unlike `23514` (`check_violation`), which PostgREST does map to `400`. Fixed by changing every `INVALID_TRANSITION` raise in this migration to `errcode = '23514'`, re-verified live (see below) — a concurrent-loser transition now correctly returns `400`. **Not retroactively fixed** in the two earlier migrations that share the same `55000` pattern (`SCOPE_LOCKED`, `SUBMISSIONS_CLOSED`) — both are from already-delivered, already-reported slices, and the bug is cosmetic in this codebase specifically because `services/rpc-error.ts`'s `mapRpcError` parses the error *message* string, never the HTTP status code, so no service-layer or UI behavior is actually affected by the wrong status. Flagged here for visibility and left as a disclosed, low-priority remaining risk rather than silently patched as a side effect of unrelated work.

**Why these RPCs cannot themselves verify the referenced object was actually uploaded, and why that gap is bounded rather than fixed here**: Postgres has no built-in way to query Supabase Storage (a separate HTTP service) from inside a `plpgsql` function without adding an extension this slice does not introduce. An already-authorized caller (a researcher on their own report, or an org manager on a report their organization already controls) could in principle call `add_*_file_evidence` directly with a well-formed but fabricated `object_key`/`sha256`/`size_bytes`. This is not a privilege-escalation or cross-tenant issue — the caller already holds exactly the authority needed to add real evidence to that same report — and a later download attempt against a fabricated key fails cleanly against a real, nonexistent object rather than exposing anything. Disclosed in `docs/decisions/0011-binary-evidence-storage.md` as a remaining risk, with a stronger mitigation (an out-of-band existence check via `pg_net`/a Storage webhook) described there, not implemented.

**Why the upload flow orders bytes-before-row, and what that does and does not guarantee**: `services/report-file-evidence.ts` writes the object to storage via `lib/evidence-store.ts`'s `EvidenceObjectStore` abstraction, computes its SHA-256 from the actual received bytes, and only then calls the finalize RPC above — so a persisted `report_evidence` row of `evidence_type = 'file'` is, by construction, proof the object exists; no separate `upload_status` column is needed because a row can only ever represent that one state. If the finalize RPC then rejects (a race, a validation failure), the orchestration layer makes a best-effort `deleteObject` call on the just-written object — confirmed live, see below. The residual case — the object write succeeds but the *entire process* crashes before the cleanup attempt runs — is not automatically remediated in this slice; the documented (not scheduled) mitigation is a future job that lists objects under `evidence/` and deletes any with no matching `report_evidence.object_key` older than 24 hours.

**Why the finality check is generic, not a hardcoded status list**: `not exists (select 1 from private.report_status_transitions t where t.from_status = report.status)` asks the transition table itself whether any legal move exists from the current status — the same table `private.is_valid_report_transition` already reads. **Why the reciprocal-duplicate check needed a second row lock, and what that lock does and does not protect against**: `private.lock_and_authorize_report_for_triage` locks only `target_report_id` (the report being marked as a duplicate). `mark_duplicate` now also locks `duplicate_of_report_id` (`SELECT ... FOR UPDATE`) before checking whether *that* report already points back at the first — without this second lock, two managers could each read the other's row as "not yet a duplicate of anything" before either write commits, and both writes would succeed, producing exactly the reciprocal relationship the check exists to prevent. Because every call to `mark_duplicate` locks in the identical order (its own `target_report_id` first, then `duplicate_of_report_id`), a genuinely simultaneous pair of opposite calls (`mark_duplicate(A, B)` and `mark_duplicate(B, A)` at the same instant) is a **real, detectable Postgres deadlock** (each transaction holds one row and waits for the other) rather than a silent race — caught with `exception when deadlock_detected` and re-mapped to the same `INVALID_DUPLICATE_TARGET` message family used for every other duplicate-target rejection, never left to leak Postgres's own `40P01` error. Confirmed live under genuine concurrency below. A longer transitive cycle (three or more reports) is not detected by this check — disclosed as a remaining risk, not silently assumed solved.

**No new columns, no new RPCs, no new capability**: this migration redefines two already-reviewed functions and adds no schema beyond what those two redefinitions touch. `classification` and `resolution_reason`/`resolution_type` were deliberately not added — see `docs/decisions/0012-report-resolution-and-classification.md` for why `report_status`'s existing terminal values and `resolution_summary` already satisfy what `DOMAIN.md` names.

### Two real bugs found during this verification and fixed in `202608260002_data_api_table_grants.sql`

### Disclosed observation (not a vulnerability): a schema-wide default-ACL grants `anon` full table privileges, neutralized entirely by RLS

While verifying `report_messages`'s grants this session, `\z public.report_messages` showed `anon=arwdDxtm` (every table privilege) despite this migration's own `grant select ... to authenticated` never mentioning `anon`. `select * from pg_default_acl` confirmed the cause: this local Supabase stack's own bootstrap (not any file in `supabase/migrations/`) sets a schema-level default ACL granting full table privileges on every future `public` table to `postgres`, `anon`, `authenticated`, and `service_role` alike, applied automatically at `CREATE TABLE` time. Every table in this schema — including `reports`, `organizations`, and every other already-delivered, already-verified table — carries the identical `anon=arwdDxtm` grant; this is not something this or any prior migration in this project introduced, and every migration's own `revoke all ... from public` / `grant select ... to authenticated` statements are, in this specific respect, redundant rather than the actual enforcement mechanism they read as. The actual enforcement is Row Level Security: every policy in this schema is declared `for select to authenticated` (or an equivalent role-scoped clause), and Postgres RLS denies all rows to a connecting role that matches zero applicable policies, regardless of what table-level `GRANT` that role separately holds — confirmed live, repeatedly, this session: an `anon`-role request against `report_messages`/`report_evidence`/`reports` returns `HTTP 200` with an empty array, never actual rows, in every scenario tested. No data exposure was found. This is flagged for visibility because the grant statements' apparent purpose (blocking `anon`) is not actually what is blocking `anon` here, which is worth knowing if this project is ever migrated to a hosted project or a stack without this default ACL preconfigured — RLS must remain the relied-upon boundary regardless of what a `\z` grant listing appears to show.

| Function | Schema | Authorization check | Client-supplied identity? | Transaction boundary | Audit event |
|---|---|---|---|---|---|

**Why there is no generic `update_program_status(status)` RPC**: identical reasoning to `0009`'s report-triage review above — each of the five functions hardcodes its own target status as a string literal in its own `update` statement; there is no code path anywhere in this migration where a `program_status` value flows from a function parameter into a `set status = ...` clause.

**Why `activate_program`/`resume_program` needed an extra check beyond `private.is_valid_program_transition`, unlike every other transition RPC in this schema**: this is the first migration where two different RPCs legitimately share a target status from two different prior states. Trusting the shared transition table alone (`is_valid_program_transition(program.status, 'active')`) would let `activate_program` fire from `paused` and `resume_program` fire from `review`, since both edges are globally legal — silently misattributing the audit event to the wrong real-world action. Each function's own additional `program.status <> 'review'` / `<> 'paused'` guard closes this without touching the shared table, which remains the single source of truth for "is this edge legal at all."

**Live verification performed this migration** (`docs/decisions/0021-program-lifecycle-transitions.md` has the full narrative): the complete legal journey (`draft→review→active→paused→active→closed`), all nine illegal edges from `draft` and from `closed` (five of which are the terminal-state check), the full authorization matrix (owner succeeds; billing_admin, a researcher with program access, a stranger with no organization relationship, and a cross-tenant organization's own owner are all rejected `FORBIDDEN`; anonymous rejected `AUTH_REQUIRED`), exact audit-event counts (1 per success, 0 per rejection, verified by direct count query after every single call in the matrix, not sampled), idempotency (a second `activate_program` call on an already-active program rejected before any write), direct-client-mutation denial (re-read after an attempted `UPDATE` confirms zero effect), and two genuine-concurrency scenarios (two identical simultaneous `close_program` calls resolve to exactly one success and one clean rejection with exactly one audit event; a simultaneous `pause_program`/`close_program` pair resolves deterministically with no impossible/torn state, though — disclosed honestly in the decision document — this specific pair is not a true mutual-exclusion case since `close_program` legally accepts the other's resulting state, so both can coherently succeed in sequence depending on lock-acquisition order). **No bugs found in this migration** — it reused `0009`'s already-proven row-locking and hardcoded-target-status patterns throughout, and its one genuinely novel design question (the shared-target-status wrinkle) was resolved before any live testing, in this document's own review, rather than discovered as a live defect.
