# Unpatched Platform architecture

## Scope

This repository implements Phase 1 and Phase 2: application plumbing, identity persistence with automatic account provisioning, tenant membership with a five-role model (Owner, Security Admin, Program Manager, Triager, Billing Admin) and a full member lifecycle (invite, accept, suspend, reactivate, remove), organization creation, an audit-log foundation covering every membership/organization/program/scope/researcher/report mutation, and eight slices of Phase 3: Program Foundation (creation only, at `DRAFT`, with organization-scoped authorization and its own program-level `manager` role), Program Scope & Asset Foundation (domain/URL/IP-CIDR scope entries with database-authoritative canonicalization and most-specific-match precedence), Researcher Access Foundation (invitation-only participation, a third authorization domain separate from organization membership and program management), Report Foundation (submission only, composing researcher/program/scope authorization; no triage transitions), Report Triage Foundation (the report lifecycle state machine — eight explicit transition RPCs, no generic status-update endpoint — plus an orthogonal organization-confirmed-severity RPC), Evidence & Secure Communication Foundation (`report_messages`/`report_evidence`, a structured, non-chat communication and evidence model with a `researcher_visible`/`internal` visibility axis enforced by RLS, superseding the one-shot information-request/response fields), Binary Evidence & Secure Object Storage Foundation (a provider-independent `EvidenceObjectStore` abstraction, Supabase Storage as its current implementation, opaque server-generated object keys, server-derived SHA-256 hashing, and authorization-gated short-lived signed downloads — no public bucket, no permanent URL, no service-role credential ever reaching the browser), Report Resolution & Classification Foundation (confirming the terminal `report_status` values already *are* the classification and `resolution_summary` already answers resolution — no redundant columns added — while making `confirmed_severity` immutable once a report is finalized and closing a reciprocal-duplicate-relationship gap, so the report row is a stable, trustworthy input boundary for a future bounty engine), Bounty Decision Engine Foundation (a bounty is a decision derived from report facts plus versioned program policy, never a property of the report row — `program_bounty_policy_versions`/`..._severity_ranges` are never edited in place, only superseded, so a later policy change can never silently rewrite an already-calculated or already-finalized `report_bounty_decisions` row; eligibility, the calculated recommendation, and the final financial decision are three separable states, not one auto-paid amount), Payment Ledger & Payout Orchestration Foundation (a finalized bounty decision is not itself a payment — `payment_obligations`/`payment_attempts` are two further, separate concepts; a provider-neutral `PaymentProvider` adapter, currently a manual-only implementation that never claims a payout succeeded until an explicit operator action records one, so the domain never imports a payment provider SDK), Transactional Outbox + Job Execution Foundation (infrastructure, not a product feature: `outbox_events`/`outbox_event_receipts` let a domain mutation durably record, in the same transaction, that another process may need to react to it, without ever placing an external side effect inside that transaction; `workers/outbox/` is a standalone worker process, never part of the Next.js app, reachable only via the `service_role` key; `submit_report` is the one instrumented reference integration, emitting a `report.created` v1 event), Researcher Reputation Ledger Foundation (a researcher's reputation is built from an immutable, append-only ledger of objectively-attributable facts — never a mutable score column and never an invented scoring formula; `reputation_ledger` records six report-outcome/bounty fact types, each re-derived server-side from the authoritative `reports`/`report_bounty_decisions` row rather than trusted from the event payload; six existing triage/bounty RPCs are redefined to also emit an outbox event, consumed by a new `workers/outbox/handlers/reputation/` consumer reusing the exact outbox machinery `0015` built, with no second queue and no second worker), and Notification Routing + Preferences + Delivery Foundation (Unpatched's first real outbox consumer beyond a reference stand-in and the reputation ledger: `route_and_create_notifications` re-derives each event's eligible recipients from the exact same authorization predicate the underlying report's own RLS policy already expresses — organization-side recipients for `report.created`, the report's own researcher for every terminal outcome/bounty event — checks each recipient's preference, and inserts a content-free `notifications` row `on conflict do nothing`, a real atomic upsert rather than a check-then-insert; `notification_deliveries` tracks at most one delivery attempt per channel, currently only `'email'`, behind a provider-neutral `lib/email-provider.ts` seam with only a development provider wired up; the outbox registry itself was extended to support multiple independent consumers per `event_type:schema_version` key, since this slice's notification consumer needed to coexist with 0016's reputation consumer on the identical keys). Production Backend Hardening & Integration Boundary (a database-backed rate-limit primitive, `private.check_and_consume_rate_limit`, applied to sign-in/report-submission/organization-creation as three representative abuse-sensitive mutations across three different authentication contexts; real keyset pagination, `types/pagination.ts`'s `Page<T>` contract, applied to every genuinely-unbounded, user-facing collection found by audit — a researcher's own report history, a program's report inbox, an organization's audit trail, and a recipient's notifications; one representative `/api/v1/reports` endpoint with a stable response envelope and a `CODE -> HTTP status` map; a structured-logging boundary with request-id correlation; and conservative HTTP security headers — none of it a new domain feature, all of it hardening the boundary the frontend build depends on), and Program Lifecycle Foundation (five purpose-built transition RPCs — `submit_program_for_review`, `activate_program`, `pause_program`, `resume_program`, `close_program` — implementing `DOMAIN.md`'s own `draft->review->active->paused->closed` lifecycle for the first time; every program created before this slice, and every one created after it, had been and remains permanently stuck at `draft` until explicitly advanced through these RPCs, reusing report-triage's exact transition-table/row-lock/hardcoded-target-status architecture rather than inventing a second one). Real provider integration, payouts, dashboards, a final reputation score, a real email provider, real webhooks, and every remaining product-facing consumer of the outbox (scanning, reconciliation) are deliberately not represented by placeholder functionality; assignment, researcher-proposed severity, malware scanning, automated orphan-object cleanup, a vulnerability-type classification taxonomy, report reopening, bounty negotiation/disputes, provider webhooks (payment or notification), reconciliation, leaderboards/badges/rankings/anti-Sybil enforcement, Slack/Teams/push/SMS/digest notification channels, a strict nonce-based CSP, and invitation/evidence-upload rate limiting are documented deferrals (see `docs/decisions/0009-report-triage-state-machine.md`, `docs/decisions/0010-report-evidence-and-communication.md`, `docs/decisions/0011-binary-evidence-storage.md`, `docs/decisions/0012-report-resolution-and-classification.md`, `docs/decisions/0013-bounty-decision-engine.md`, `docs/decisions/0014-payment-ledger-and-payout-orchestration.md`, `docs/decisions/0015-outbox-event-foundation.md`, `docs/decisions/0016-reputation-ledger-foundation.md`, `docs/decisions/0017-notification-routing-and-delivery-foundation.md`, `docs/decisions/0018-production-hardening-and-integration-boundary.md`), not fabricated data.

## Layers

`app/` renders Next.js App Router pages. Route handlers and Server Actions will authenticate before calling `services/`. `services/` owns authorization and domain rules. `lib/` contains integration code such as the native Postgres pool, environment parsing, and the current-session lookup. Database truth lives in PostgreSQL migrations under `db/migrations/`; TypeScript types are convenience types, not authorization evidence.

## Identity and tenancy

Supabase Auth owns credentials and sessions in `auth.users`. `public.users` is a one-to-one application profile keyed by the Auth UUID and is created automatically by an `auth.users` insert trigger (`handle_new_auth_user`), which also denormalizes `email` onto the profile (kept in sync by a second trigger) so RLS-scoped reads never need to touch the protected `auth` schema. Organizations are tenants. `organization_members` is the authoritative membership relation and has a composite primary key to prevent duplicate memberships. A global platform role is limited to platform-wide moderation; organization privileges always require membership.

## Authorization

Authorization is performed server-side and reinforced by Row Level Security; browser-provided IDs, roles, and ownership are not trusted. As of the 202608260001 migration, every organization-membership mutation (invite, accept, cancel, role change, suspend, reactivate, remove) goes through a `SECURITY DEFINER` Postgres function that re-derives the actor from `auth.uid()` and re-checks authorization against current database state, rather than through a service-role client. This intentionally minimizes service-role key usage per `SECURITY.md`; see `docs/decisions/0001-rpc-based-membership-mutations.md` for the full rationale and the trade-off it accepts. Reads rely on RLS policies scoped through `SECURITY DEFINER` helper functions (`is_org_member`, `has_org_role`, `shares_organization_with`) to avoid Postgres's self-referencing-policy recursion; these helpers live in a `private` schema, not `public`, so PostgREST never exposes them as directly callable RPC endpoints (`supabase/config.toml`'s `[api] schemas` does not list `private`) — see `docs/security/phase-2-rpc-review.md` and `docs/decisions/0002-authentication-and-backend-boundary.md` for the finding this corrected. Authentication is Supabase Auth, wired through `middleware.ts` (session refresh), `lib/auth/current-user.ts` (re-validated via `auth.getUser()`, never `auth.getSession()`), and `/sign-in`/`/sign-up`/`/auth/confirm`.

## Database decisions

The first migration created the tables required for Phase 1: application user profiles, optional researcher-profile details, tenant organizations, tenant membership, and append-oriented audit records. The second migration (202608260001) evolved the three-value Phase 1 role enum into the five-role Phase 2 model, added member/organization lifecycle status, added `organization_invitations`, and added account provisioning. The third migration (202608260002) fixed a real bug found during live verification: no base `GRANT SELECT` existed for `authenticated` on any table, so RLS was correctly configured but unreachable. The fourth migration (202608260003) added organization creation: a `create_organization` RPC (atomic — organization, owner membership, and audit event in one transaction), a per-creator unique `idempotency_key` on `organizations` for genuine database-level double-submission protection, and two RLS-boundary-respecting ways for an invitee to discover and accept an invitation without an org admin's help (`list_my_pending_invitations`, `accept_organization_invitation_by_id`). The fifth migration (202608260004) added Program Foundation: `programs` and `program_members` tables (a program-level role distinct from any organization role — see `docs/decisions/0004-program-authorization.md`), a `create_program` RPC restricted to organization Owner/Security Admin and authorized against the caller's real, current organization membership rather than a trusted client-supplied id, the same per-(organization, creator) idempotency-key pattern organization creation established, and a `private.is_program_member` RLS helper following the exact non-exposed pattern `private.is_org_member` set. The sixth migration (202608260005) added Program Scope & Asset Foundation: `program_scope_entries` (three asset types, native Postgres `cidr` for IP/CIDR targets rather than hand-rolled string matching, a partial unique index preventing duplicate active targets after canonicalization), a `private.canonicalize_scope_target` helper that is the single, authoritative place validation/normalization happens (never duplicated in TypeScript — see `docs/decisions/0006-scope-asset-model.md`), `add_scope_entry`/`update_scope_entry`/`remove_scope_entry` (soft-delete only, never a physical `DELETE`), and `evaluate_program_scope`, an internal (not researcher-facing) most-specific-match scope-decision RPC. The seventh migration (202608260006) added Researcher Access Foundation: `program_invitations`/`program_researchers` (a third authorization domain, distinct from `organization_members` and `program_members` — see `docs/decisions/0007-researcher-access.md`), a `private.is_researcher_authorized_for_program` RLS helper (single-parameter, deriving the actor from `auth.uid()`, the same shape every other private helper in this schema uses, deliberately, so it can never become an arbitrary-researcher-id oracle), widened `programs`/`program_scope_entries` read policies so an active researcher can read the program and its currently-active scope only, and a real bug found live and fixed in the same migration: `public.users`' read policy had no path for a program manager to read a researcher's profile (a researcher shares no organization with the manager by design), so a researcher's name/email on the manager-facing roster silently resolved to null — fixed with a narrowly-scoped third read policy, resolved from the real `program_researchers` relationship, never a client-supplied id. The eighth migration (202608270001) added Report Foundation: `reports` (a frozen scope-authorization snapshot on every row — `matched_scope_entry_id`, `matched_scope_state`, `matched_target` — so a report's historical validity never depends on the scope entry's current state), a `submit_report` RPC that composes `private.is_researcher_authorized_for_program`, a program-lifecycle check (blocked only while `paused`/`closed`), `private.canonicalize_scope_target`, and a newly-extracted `private.match_program_scope` (see below), and `list_my_reports` following the exact `list_my_program_participations` pattern for the researcher's own cross-status report history. The ninth migration (202608270002) added Report Triage Foundation: `private.report_status_transitions`, DOMAIN.md's lifecycle table implemented once as data rather than duplicated across eight hand-written IF-chains, checked via `private.is_valid_report_transition`; `private.lock_and_authorize_report_for_triage`, a shared `SELECT ... FOR UPDATE` + the same two-path manager check every other program-management mutation uses, called by every manager-facing transition RPC; eight transition RPCs (`start_triage`, `request_information`, `accept_report`, `mark_duplicate`, `mark_informative`, `mark_not_applicable`, `reject_report`, `resolve_report`), each hardcoding its own target status rather than accepting one as a parameter — deliberately, so no generic status-update endpoint can ever exist; a ninth, researcher-authorized (not manager-authorized) `respond_to_information_request` that never itself changes `status`; a tenth, state-machine-orthogonal `set_report_severity`; and five new `reports` columns for durable current-state fields (`confirmed_severity`, `duplicate_of_report_id`, `information_request_reason`, `researcher_response`, `resolution_summary`) rather than a generic jsonb escape hatch. No new table beyond the transition-rule table itself — `audit_logs`, already required by `SECURITY.md`, is reused as the decision-history record; see `docs/decisions/0009-report-triage-state-machine.md` for why a dedicated report-history table was considered and rejected. The tenth migration (202608270003) added Evidence & Secure Communication Foundation: `report_messages` and `report_evidence` (two distinct tables — communication vs. supporting material — each tied to its report by a real composite foreign key to a new `reports(id, program_id, organization_id)` unique constraint, each with a `report_visibility` enum column, `researcher_visible`/`internal`, enforced by RLS, never inferred from report access alone); `private.authorize_report_for_communication`, a non-locking sibling of `private.lock_and_authorize_report_for_triage` for pure appends; `private.insert_report_message`/`private.insert_report_evidence`, shared non-authorizing insert primitives following the `private.match_program_scope` pattern; four public RPCs (`post_researcher_message`, `post_organization_message`, `add_researcher_evidence`, `add_organization_evidence`); `reports.information_request_reason`/`researcher_response` dropped and superseded by `report_messages` rows (`request_information` redefined to match); and both new tables deliberately append-only (no update/delete RPC) in this slice. See `docs/decisions/0010-report-evidence-and-communication.md`. The eleventh and twelfth migrations (202608270004, split from 202608270005 solely because Postgres refuses to use a freshly-added enum value inside a check constraint within the same transaction that added it) added Binary Evidence & Secure Object Storage Foundation: `report_evidence_type` gains a `'file'` value; `report_evidence` gains five nullable columns (`object_key`, `original_filename`, `content_type`, `size_bytes`, `sha256`) with a check constraint enforcing exactly one shape per row (file rows carry every file field and no `content`; every other type keeps `content` and no file fields); a private `evidence` storage bucket (`public = false`, a 10 MiB storage-layer size limit behind the application's own identical check constraint); `private.authorize_report_for_communication` reused unchanged; `private.insert_report_file_evidence`, the file-shaped sibling of `0010`'s insert primitive; `add_researcher_file_evidence`/`add_organization_file_evidence` (called only after the object already exists in storage — see below); and `record_evidence_download`, which independently re-derives the same visibility predicate `report_evidence`'s own RLS policy expresses before recording a `report.evidence_downloaded` audit event. No `upload_status` column exists — see `docs/decisions/0011-binary-evidence-storage.md` for why the bytes-before-row upload ordering makes one unnecessary, and for the disclosed, bounded residual risk this ordering does not close. The thirteenth migration (202608280001) added Report Resolution & Classification Foundation: no new "classification" column (DOMAIN.md's own terminal `report_status` values — `resolved`/`duplicate`/`informative`/`not_applicable`/`rejected` — already are the classification) and no new resolution field (`resolution_summary`, from `0009`, already answers what DOMAIN.md names); `set_report_severity` redefined to reject (`SEVERITY_LOCKED`) once a report has reached any terminal state, checked generically against `private.report_status_transitions` rather than a hardcoded status list; `mark_duplicate` redefined to additionally lock the target report row and reject a reciprocal duplicate relationship (a report marked as a duplicate of a report that is itself already marked as a duplicate of the first), with a genuine simultaneous race caught as a Postgres deadlock and re-mapped to a safe message rather than left to leak raw. No reopening operation exists — DOMAIN.md states directly that terminal outcomes have no exit transition. See `docs/decisions/0012-report-resolution-and-classification.md`. The fourteenth migration (202608280002) added Bounty Decision Engine Foundation: `program_bounty_policy_versions`/`program_bounty_policy_severity_ranges` (a versioned policy, reusing `public.report_severity` from `0009` rather than a second taxonomy, all five tiers mandatory as explicit numeric RPC parameters rather than an optional jsonb array, `superseded_at` plus a real `unique(program_id, version_number)` constraint meaning a version is never edited in place, only ever superseded) and `report_bounty_decisions` (one row per report — `state` in `ineligible`/`calculated`/`finalized`, a shape check constraint enforcing exactly one valid column combination per state, a composite FK to `program_bounty_policy_versions(id, program_id)` alongside the existing `reports(id, program_id, organization_id)` FK from `0010`, so a decision can never reference another tenant's report or another program's policy version at the database layer, independent of RPC discipline); `private.lock_and_authorize_report_for_finance`, a materially narrower sibling of `0009`'s `private.lock_and_authorize_report_for_triage` (owner/security_admin only, no program-manager fallback, since committing an actual financial figure is more sensitive than ordinary triage) locking the same `reports` row so finance and triage operations serialize against each other; `calculate_bounty_recommendation` (broad triage authorization, produces a recommendation — a retryable precondition such as an unconfirmed severity or a missing policy writes no row, while a permanent classification fact such as a non-`resolved` terminal status writes a real, stored `ineligible` row, and a guard added before any other logic rejects recalculating an already-`finalized` decision, closing a silent-overwrite bug caught in this migration's own design review before any live testing); `finalize_bounty`/`adjust_bounty` (both narrow-authorization; finalizing an already-finalized decision is rejected by name — the same idempotency-as-rejection choice `0009` made for status transitions — and an adjustment always records the previous amount, new amount, and a reason rather than a bare `UPDATE`). All money is `bigint` minor units with a format-checked (not list-validated) ISO-4217-shaped currency column; no floating-point arithmetic exists anywhere in this migration or in `lib/money.ts`'s pure string-based conversions. See `docs/decisions/0013-bounty-decision-engine.md`. PostgreSQL enums constrain persisted roles and statuses. Foreign keys, checks, uniqueness constraints, and RLS are used where they express invariant rules. A future migration should add a generic `set_updated_at` trigger rather than relying on every mutation path to set it explicitly.

Report Foundation's own migration (202608270001) additionally factored `evaluate_program_scope`'s matching logic out into `private.match_program_scope` — a deliberate, non-self-authorizing exception to this schema's usual private-helper pattern, since `submit_report` needed the same matching decision `evaluate_program_scope` already made, but under a completely different (researcher, not manager) authorization gate that the original function's own internal check would have rejected. `evaluate_program_scope` was redefined (not duplicated) to call the same shared helper; the refactor was re-verified live to confirm it introduced no behavioral regression. See `docs/decisions/0008-report-authorization-and-scope-snapshot.md`.

Report Triage Foundation's own migration (202608270002) introduces this schema's first genuinely concurrency-sensitive authorization helper: `private.lock_and_authorize_report_for_triage` locks the target report row (`SELECT ... FOR UPDATE`) before authorizing and returning it, so two managers racing to transition the same report serialize on the row rather than both reading a stale `status` and both succeeding — verified live with two truly parallel conflicting transition requests, which resolved to exactly one winner and one cleanly-rejected loser. It also introduces this schema's first RPC with an authorization check deliberately *different* from its sibling RPCs in the same migration: `respond_to_information_request` is researcher-authorized (`report.researcher_id = auth.uid()`, the same shape `submit_report` uses), not manager-authorized, since the manager-only helper would have rejected the very researcher the function exists for. See `docs/decisions/0009-report-triage-state-machine.md`.

Evidence & Secure Communication Foundation's own migration (202608270003) introduces this schema's first *cross-user* RLS helper: `private.is_manager_or_admin_of_my_program(candidate_user_id)`, which self-authorizes the caller via `auth.uid()` but asks about a *different* user (is this candidate a manager or org admin of one of my authorized programs), needed so a researcher reading a message/evidence row can resolve its organization-authored author's display name. A first attempt inlined the equivalent `exists()` query directly in the `users` policy body, mirroring `0007`'s own manager-reads-researcher policy shape — live verification (simulating a researcher's session directly against Postgres) caught that this does not work in reverse: the inline subquery is itself subject to `program_members`'/`organization_members`' own RLS, which grants a plain researcher no read path to either table, so the `exists()` silently evaluated `false` regardless of the real relationship. The fix follows this schema's own established pattern for exactly this failure mode: a `SECURITY DEFINER` helper that bypasses the subquery tables' RLS internally, the same way `private.has_org_role`/`private.is_program_member` already do for every other cross-table RLS check in this codebase. See `docs/decisions/0010-report-evidence-and-communication.md`.

Binary Evidence & Secure Object Storage Foundation's migrations introduce this schema's first genuinely cross-service consistency problem: object storage and PostgreSQL do not share one ACID transaction. The resolution is an ordering discipline, not a status column — `services/report-file-evidence.ts` writes the object to the private bucket via `lib/evidence-store.ts`'s `EvidenceObjectStore` abstraction (`putObject`) *before* calling either finalize RPC, and attempts a best-effort `deleteObject` cleanup if the RPC then rejects — so a persisted `report_evidence` row of `evidence_type = 'file'` is, by construction, proof its object exists, without needing a column that could only ever hold one value. Download authorization reuses the RLS policy `0010` already established: a session-scoped read of `report_evidence` decides whether the caller may proceed at all (denied and nonexistent are indistinguishable), and only then does a server-only service-role client mint a 60-second signed URL via `createSignedUrl(..., { download: filename })` — verified live, including against the underlying `@supabase/storage-js` SDK source, that the `download` option is what forces `Content-Disposition: attachment` on the response regardless of the file's stored content type, the actual control preventing a maliciously-labeled file from ever being rendered inline by a browser. See `docs/decisions/0011-binary-evidence-storage.md`.

Report Resolution & Classification Foundation's own migration (202608280001) is this schema's first to add a rule specifically because a *future, not-yet-built* slice will depend on it: `confirmed_severity` becoming immutable once a report is terminal is not stated anywhere in `DOMAIN.md`; it is justified entirely by this task's own "10× future economics" requirement that a bounty engine must be able to consume confirmed severity without the report schema changing again. It also closes this schema's first *relationship-integrity* gap between two rows of the same table: nothing previously stopped two reports from referencing each other as duplicates (`A.duplicate_of_report_id = B.id` and `B.duplicate_of_report_id = A.id` simultaneously) — `mark_duplicate` now locks both rows and rejects the reciprocal case, and a genuinely simultaneous attempt at both directions produces a real Postgres deadlock, deliberately caught and re-mapped rather than left to surface as a raw, unmapped error. See `docs/decisions/0012-report-resolution-and-classification.md`.

Bounty Decision Engine Foundation's own migration (202608280002) is the first to separate a *recommendation* from a *decision* as two different verbs on the same row rather than one write: `calculate_bounty_recommendation` and `finalize_bounty` are different RPCs, gated by different authorization helpers, so a policy-table bug or an unauthorized triager can produce a wrong recommendation that is merely wrong, never a wrong payment — only `finalize_bounty`/`adjust_bounty`, owner/security_admin-only, commit a `final_amount_minor_units`. It is also this schema's first migration to prove a *historical-immutability* property live rather than merely by inspection: a report finalized under bounty policy V1 was confirmed, via a direct database read after publishing policy V2 with different severity ranges, to retain its original V1-derived amount unchanged, while a fresh calculation on a different report picked up V2 — the composite FK from `report_bounty_decisions.policy_version_id` to `program_bounty_policy_versions(id, program_id)` is what makes this a database guarantee rather than an application convention. A direct service-role SQL insert attempting to attach a different program's policy version to a report was independently confirmed to fail on this same constraint, bypassing RLS and all RPC code entirely. See `docs/decisions/0013-bounty-decision-engine.md`.

Payment Ledger & Payout Orchestration Foundation's own migration (202608290001) is the first to separate a *financial decision* from a *financial transaction* as two different tables with two different lifecycles, rather than one row acquiring more columns: `report_bounty_decisions` (what is owed) is never altered by this migration at all, and `payment_obligations`/`payment_attempts` (whether it has actually been paid) have their own independent state machines. It is also this schema's first migration to prove *provider independence* live rather than by inspection: `services/payments.ts` was confirmed, by direct source inspection across every file touching the payment domain plus a `package.json` dependency check, to contain no reference to any payment provider SDK — the only file that ever could is `lib/payment-provider.ts`, the deliberate adapter seam. A genuinely concurrent pair of `create_payment_obligation` calls against the same finalized decision, and a genuinely concurrent pair of `initiate_manual_payment_attempt` calls against the same obligation, were each independently confirmed live to produce exactly one success and one clean, mapped rejection — never two rows. See `docs/decisions/0014-payment-ledger-and-payout-orchestration.md`.

Transactional Outbox + Job Execution Foundation's own migration (202608290002) is the first to introduce a genuinely standalone runtime process (`workers/outbox/run.ts`, invoked via `npm run worker:outbox`, never imported by `app/`/`actions/`/`services/`/`components/` — confirmed by a direct grep across all four) alongside the Next.js application itself, and the first to grant a table/RPC set to `service_role` while explicitly revoking it from `authenticated`/`anon` entirely, rather than relying on RLS alone — verified live as a real Postgres permission error (`42501`), not merely an RLS-filtered empty result, for an anonymous request, an authenticated researcher, and a direct RPC call from an authenticated org owner. It is also the first migration whose own live verification proved a genuine multi-process property: six truly concurrent worker jobs claimed batches from 120 seeded events (plus one incidental, unrelated event whose earlier test lease had since expired, correctly reclaimed by the same mechanism) with zero double-claims and zero lost events, and a single crashed-worker simulation (claim, then never complete) was confirmed to become reclaimable by a second worker once its lease expired, without any separate reaper process. See `docs/decisions/0015-outbox-event-foundation.md`.

The fifteenth migration (202608290001) added Payment Ledger & Payout Orchestration Foundation: `payment_obligations` (a financial snapshot copied exactly once from a *finalized* `report_bounty_decisions` row — `bounty_decision_id` is `unique`, the one-to-one invariant enforced by Postgres, not application code — with composite FKs new to this migration: `(report_id, researcher_id) → reports(id, researcher_id)` and `(bounty_decision_id, report_id) → report_bounty_decisions(id, report_id)`, so a client can never substitute a different researcher or a different report's bounty decision, independently verified live via a direct service-role attack against each) and `payment_attempts` (one or more per obligation; only three states exist — `requires_operator_action`/`succeeded`/`failed` — a fourth, async-provider-only state is deliberately omitted since nothing in this migration can produce it, the same precedent `202608270004` set for `report_evidence_type`'s `'file'` value arriving in its own migration ahead of the constraint using it); `private.lock_and_authorize_obligation_for_finance`, the obligation-keyed sibling of `0013`'s report-keyed finance helper, identical narrow (owner/security_admin-only) authorization; `create_payment_obligation` (reuses `0013`'s `private.lock_and_authorize_report_for_finance` unchanged, additionally locks the decision row itself so the "does an obligation already exist" check is race-free); `initiate_manual_payment_attempt` (hardcodes `provider = 'manual'` — no generic `initiate(provider)` RPC exists, the identical anti-pattern-avoidance `0009` already established for report status transitions); `record_manual_payment_result` (the only path to `succeeded`/`failed` — never a side effect of initiation); and `cancel_payment_obligation` (legal only from `pending`/`failed`). `services/payments.ts` never imports a payment provider SDK — it imports only `lib/payment-provider.ts`'s `PaymentProvider` interface, mirroring `lib/evidence-store.ts`'s `EvidenceObjectStore` seam from `0011`. See `docs/decisions/0014-payment-ledger-and-payout-orchestration.md`.

The sixteenth migration (202608290002) added Transactional Outbox + Job Execution Foundation: `outbox_events` (`event_type`/`schema_version`/`aggregate_type`/`aggregate_id`/`organization_id`/`payload`, only four reachable states — `pending`/`processing`/`succeeded`/`dead_letter` — with a shape check constraint tying `locked_at`/`locked_by` to `status = 'processing'` exactly, and two partial indexes matching the claim query's own predicate) and `outbox_event_receipts` (a `(consumer_name, event_id)`-keyed idempotency ledger a handler writes to before performing its side effect); `claim_outbox_events` (`FOR UPDATE SKIP LOCKED` inside one atomic function, so any number of concurrent worker processes never double-claim a row; also dead-letters an abandoned, attempts-exhausted lease before claiming, closing an eternal-crash-loop gap a naive lease-expiry reclaim alone would leave open) and `complete_outbox_event` (the only path out of `processing`; requires the caller to still hold the lease it claimed, rejecting `LEASE_LOST` otherwise; `p_permanent` bypasses the attempts/backoff calculation entirely for a failure that can never succeed on retry) — both revoked from `public`/`authenticated`/`anon` entirely and granted only to `service_role`, reachable only from `workers/outbox/client.ts`'s standalone Supabase client, never from any Next.js route or Server Action. `submit_report` (`0008`) is redefined, not duplicated, to add exactly one more insert — a `report.created` v1 outbox event — after its existing `reports` and `audit_logs` inserts, in the same transaction; no other existing RPC (bounty, payment) is modified. See `docs/decisions/0015-outbox-event-foundation.md`.

The seventeenth migration (202608290003) added Researcher Reputation Ledger Foundation: `reputation_ledger` (`fact_type` constrained to exactly six values — `report_resolved`/`report_duplicate`/`report_informative`/`report_not_applicable`/`report_rejected`/`bounty_finalized` — with no numeric score/value/points column of any kind, so it is structurally impossible to encode a scoring formula into this table; two composite FKs, `(report_id, program_id, organization_id) → reports(id, program_id, organization_id)` and `(report_id, researcher_id) → reports(id, researcher_id)`, so a ledger row can never disagree with the report it claims to be about; `source_event_id unique`, the idempotency boundary; a reserved, unpopulated `compensates_fact_id` self-FK for a future correction mechanism the domain does not yet have; a real append-only trigger, `private.reject_reputation_ledger_mutation`, attached to both `UPDATE` and `DELETE`, verified live to reject even a maximally-privileged direct `psql` connection). `record_reputation_fact`/`record_bounty_finalized_reputation_fact` (both `service_role`-only, both re-deriving every provenance field from the authoritative `reports`/`report_bounty_decisions` row rather than the event payload, both independently re-verifying the report's actual current status against the claimed fact type — `PROVENANCE_MISMATCH` otherwise — and both wrapping their insert in an exception handler catching `unique_violation`, so a genuinely concurrent duplicate call returns the winning row instead of a raw Postgres error, a fix driven by live concurrency testing rather than assumed safe) and `get_my_reputation_summary` (self-only via `auth.uid()`, no parameter, returning plain `fact_type`/count aggregates, never a raw row). Six existing RPCs (`resolve_report`, `mark_duplicate`, `mark_informative`, `mark_not_applicable`, `reject_report`, `finalize_bounty`) are redefined, not duplicated, each adding exactly one `outbox_events` insert after its existing `audit_logs` insert, in the same transaction — every prior line of logic preserved exactly. Unlike `0015`'s zero-RLS-policy `outbox_events` (which has no legitimate human reader), `reputation_ledger` follows this schema's normal RLS pattern (owning researcher OR the report's own organization), since it has two legitimate human readers. See `docs/decisions/0016-reputation-ledger-foundation.md`.

The eighteenth migration (202608290004) added Notification Routing + Preferences + Delivery Foundation: `notifications` (content-free by design — no report title/description/bounty amount column exists anywhere on it; `category`/`notification_type` each constrained to a small enumerated set, tied together by a shape-check constraint; `unique (source_event_id, recipient_id)`, the fan-out idempotency boundary, enforced via `on conflict do nothing` rather than a check-then-insert; the same `(report_id, program_id, organization_id)` composite FK `0016` established against `reports`, but deliberately no `researcher_id` column or FK — unlike `reputation_ledger`, a notification's recipient is not constrained to the report's own researcher, since an organization-side recipient is a legitimate, different audience for the same report), `notification_deliveries` (one row per notification per channel — currently only `'email'` is valid; a five-state machine, `pending`/`processing`/`delivered`/`retryable_failure`/`permanent_failure`, with retries driven entirely by the existing `outbox_events` retry loop rather than any new scheduling mechanism; RLS enabled with zero policies and zero grants to `authenticated`/`anon`, mirroring `outbox_events`' own reasoning since delivery mechanics have no legitimate human reader in this slice), and `notification_preferences` (a sparse override table — a row exists only once a user actively changes a category away from its default, never one row per user at signup; `category` constrained to exactly the one configurable value, `report_activity` — `bounty_activity` is mandatory and has no override row possible at all). `route_and_create_notifications` (plain, not `security definer`, service_role-only — the identical `record_reputation_fact` reasoning) re-derives recipients via two new private helpers, `private.resolve_report_organization_recipients` and `private.can_currently_read_report`, both literally re-implementing the reports table's own existing read-RLS predicate rather than a second, divergent authorization rule; the latter is also called by `prepare_notification_email` immediately before returning any email content, re-verifying the recipient's current authorization independently of the (historical, frozen-at-creation-time) fact that a notification row already exists for them — verified live that a recipient whose access was revoked after notification creation but before email rendering receives no content at all, only a permanently-failed delivery. This migration also required, and was granted, `usage on schema private to service_role` — the first plain (non-`security definer`) function in this schema to call directly into `private.*`, since every prior caller of a private helper was either an RLS policy body or itself `security definer`. Six existing report/bounty RPCs are read but not modified by this migration — it is purely additive on the consumption side. `workers/outbox/registry.ts`/`worker.ts` were extended, in this same slice, to support multiple independent consumers per `event_type:schema_version` key (a real architectural gap found by mapping the existing registrations before implementing: every report-outcome/`bounty.finalized` key already had a reputation consumer from `0016`, and this slice's notification consumer needed to register against the identical keys without silently replacing it). See `docs/decisions/0017-notification-routing-and-delivery-foundation.md`.

The nineteenth migration (202608290005) added Production Backend Hardening & Integration Boundary: `private.rate_limit_counters` (a fixed-window counter, one row per `(bucket_key, window_start)`) and `private.check_and_consume_rate_limit` (one atomic `insert ... on conflict do update ... returning`, not a check-then-increment — the exact race class 0016 had to patch after the fact, avoided here from the start), applied to three representative, server-derived-identity-keyed mutations across three different authentication contexts: `check_sign_in_rate_limit` (a new, `security definer` public wrapper — the one pre-auth boundary in this schema, so its caller is necessarily `anon`, which has no `USAGE` on the `private` schema at all, the same gap 0017's `mark_notification_read` already bridges the same way; keyed by the normalized email being attempted, never revealing whether that account exists), `submit_report` (redefined, one rate-limit check added, keyed by the actor id, every prior line of logic unchanged), and `create_organization` (redefined identically, keyed by the actor id, deliberately distinct from the existing per-creator idempotency key, which prevents a duplicate of the *same* organization, not repeated creation of *many*). `list_my_reports` was also redefined to add real keyset pagination (`p_limit`/`p_before_submitted_at`/`p_before_id`, all defaulted for backward compatibility) — its old zero-argument overload is explicitly `drop`ped first, since `create or replace` with a new argument list does not replace an existing overload of a different arity, which would otherwise have left every existing zero-arg caller silently stuck on the stale, unpaginated version forever. Both `types/pagination.ts`'s `Page<T>` contract and `lib/pagination.ts`'s opaque cursor encoding are also applied, TypeScript-side only (no further migration needed), to `listReportsForProgram`, `getOrganizationAuditActivity`, and `getMyNotifications`, since all three are plain RLS-scoped table selects whose existing indexes (`reports_program_id_idx`, `audit_logs_organization_created_idx`, `notifications_recipient_id_created_at_idx`) already supported the new predicate/ordering with no schema change required. See `docs/decisions/0018-production-hardening-and-integration-boundary.md`.

The twentieth migration (202608290006) added Public Onboarding Abuse Hardening: `invite_organization_member` and `invite_researcher_to_program` redefined identically to `submit_report`/`create_organization`'s own 0018 pattern — one rate-limit check added immediately after `AUTH_REQUIRED`, keyed by the actor id (`'org_invite:'`/`'program_invite:' || actor::text`), 20/hour, every prior authorization/insert/audit line and the pre-existing per-`(organization-or-program, email)` unique-index destination-level guard (`INVITATION_PENDING`) unchanged. A new `check_evidence_upload_rate_limit()` (`security definer`, keyed by `'evidence_upload:' || actor::text`, 20/hour) is deliberately a standalone RPC, not folded into `add_researcher_file_evidence`/`add_organization_file_evidence` — those finalize RPCs are only ever reached after the (expensive, up to 10 MiB) storage write already happened, so `services/report-file-evidence.ts`'s `uploadAndFinalize` calls this new RPC first, immediately after cheap local validation and strictly before any storage I/O, closing the "rate-limited request must never create a storage object" requirement at the TypeScript-service layer rather than the database-RPC layer, the one place in this migration where that was actually necessary. All three new checks were verified live under genuine concurrent load (25 truly parallel requests against a 20/hour limit producing exactly 20 successes in every case) and live tenant isolation (one actor's organization exhausting its owner's budget has zero effect on a second, unrelated organization's owner, since the bucket key is always the actor's own id, never a client-supplied organization/program id). See `docs/decisions/0019-public-onboarding-abuse-hardening.md`.

SSR/CSR date-rendering consistency: a real hydration mismatch (server and browser resolving `toLocaleString(undefined, ...)`'s omitted locale/timezone differently) was found live on the report detail page and traced to ~20 independent local formatter copies with no shared, environment-pinned implementation. Consolidated into `lib/format-date.ts` (`formatDate`/`formatDateTime`), explicitly pinning locale (`en-US`, matching the codebase's existing American-English convention) and time zone (`UTC`, since no per-viewer timezone preference exists anywhere in this domain model, and a server render has no reliable signal for a visitor's real timezone without new client-only architecture) — a deliberate, disclosed display-policy decision, not a silent one, and not a change to any stored timestamp, API contract, or audit/notification value. See `docs/decisions/0020-ssr-csr-date-rendering-consistency.md`.

The twenty-first migration (202608300001) added Program Lifecycle Foundation: `private.program_status_transitions` (DOMAIN.md's five-state lifecycle as data, the identical pattern `private.report_status_transitions` from `0009` already established — `draft->review->active->paused->closed`, `closed` terminal with no outgoing row) and `private.lock_and_authorize_program_for_lifecycle` (mirrors `private.lock_and_authorize_report_for_triage` exactly — `SELECT ... FOR UPDATE` plus the identical two-path owner/security_admin-or-program_members check every other program-management mutation already uses). Five purpose-built RPCs cover the six legal edges with no generic status setter: `submit_program_for_review`, `activate_program`, `pause_program`, `resume_program`, `close_program` — the first two of which share a target status (`active`) from two different, non-interchangeable prior states (`review` for first go-live, `paused` for recovery), a wrinkle report-triage never had, resolved by each function additionally asserting its own expected prior status before deferring to the shared transition table, rather than trusting the table alone to disambiguate which specific RPC is correct for which specific prior state. Idempotency needed no new mechanism (an already-`active` program rejects a second `activate_program` call the instant its hardcoded prior-status check fails). Concurrency reused `0009`'s exact row-locking proof method, live: two genuinely simultaneous identical `close_program` calls against the same program resolved to exactly one success and one clean rejection with exactly one audit event, while a genuinely simultaneous `pause_program`/`close_program` pair demonstrated that row-level serialization does not force two individually-legal operations to be mutually exclusive when one of them (`close_program`) legitimately accepts the other's resulting state as a valid source — both outcomes were the *correct* behavior, not a bug, and are documented as such rather than the task's own suggested framing being taken at face value. This migration's own live direct-mutation-denial test (`\dp public.programs`) re-confirmed `docs/security/phase-2-rpc-review.md`'s existing "Disclosed observation" about this schema's default ACL (Supabase's local bootstrap grants broad table privileges to `authenticated`/`anon` on every `public` table regardless of each migration's own narrower `GRANT` statements) — RLS policy absence, not the `GRANT` lines, is and remains the actual protection against direct client mutation of `programs.status`. See `docs/decisions/0021-program-lifecycle-transitions.md`.

Real Email Provider Integration adds no new migration — it is a pure application-layer slice behind `0017`'s already-shipped `lib/email-provider.ts` seam. `EMAIL_PROVIDER=dev|resend` (default `dev`) selects, once at module load, either the unchanged `devEmailProvider` or a new Resend adapter that calls `https://api.resend.com/emails` directly via `fetch` (no new npm dependency — the same minimalism precedent `lib/money.ts` already set) using the caller's existing `notification_deliveries.id` as Resend's own `Idempotency-Key` header, with a deterministic retryable/permanent classification (429/5xx/network-error/ambiguous-2xx retryable; 400/401/403/422 permanent) that defaults ambiguous or unrecognized responses to retryable, deferring to `record_email_delivery_result`'s own `max_attempts` bound rather than a client-side guess about permanence. Selecting `resend` without `RESEND_API_KEY`/`EMAIL_FROM` throws immediately at module load, not on first send. Live-verified: a real HTTP round trip against the real Resend API (no valid credentials exist in this environment, so an intentionally invalid key was used) returned a genuine `401`, correctly classified permanent, proving request construction and error classification against the real provider without claiming a real delivery; separately, the full existing pipeline was re-exercised end to end with the unchanged dev provider (a real report submitted through the real API, processed by the real running outbox worker) and reached `notification_deliveries.state = 'delivered'`, confirming no regression. See `docs/decisions/0022-real-email-provider-integration.md` for the full error-classification table and an explicit statement of what remains dependent on real credentials (a genuine successful delivery to a real inbox).

Authentication Experience 2026 adds no new migration — it redesigns sign-in/sign-up within Unpatched's existing visual language and adds the previously-missing password-recovery flow (`/forgot-password` → `/reset-password`), a shared accessible password-visibility toggle, and length-first (no fabricated composition rules) password-strength feedback. It also fixes two real, previously-shipped bugs in `app/auth/confirm/route.ts` found only through live browser verification: the route's cookie adapter (built for Server Components/Actions via `next/headers`) never actually persisted the verified session onto a manually-constructed `NextResponse.redirect`, and separately, the redirect target was built from `request.url`, which Next's dev server reports with a fixed "localhost" host regardless of the client's actual host — since the session cookie is host-scoped, redirecting to a different hostname than the one that set it meant the browser correctly withheld the cookie on the next request. Both are now fixed by building a request-scoped client that writes cookies directly onto the returned response, using the request's own `Host` header for the redirect origin — the same request-cookies-in/response-cookies-out pattern `lib/supabase/middleware.ts` already used successfully. This transparently also fixes signup email-confirmation, which shares the identical route, currently unreachable in local dev only because `enable_confirmations = false`. Passkeys were evaluated and deliberately deferred: the installed `@supabase/auth-js` marks passkey methods "experimental," and this project's own `supabase/config.toml` has `[auth.passkey]` commented out — not enabled here. Account-enumeration safety (`requestPasswordResetAction` returning an identical response for a real and a fabricated email) was verified both by direct script call and live in a real browser. See `docs/decisions/0023-authentication-experience-2026.md`.

Platform Operations Foundation adds one migration introducing Unpatched's first real third-party authority: `public.platform_admins`, a real membership table (mirroring `organization_members`/`program_researchers`'s own shape, never a mutable role column) checked via `private.is_platform_admin()`, granted only by `service_role` with zero grant to `authenticated` — no self-escalation path exists through any client-reachable code, verified live. Three narrow, SECURITY DEFINER reads (`list_needs_recovery_outbox_events`/`_notification_deliveries`/`_payment_attempts`) expose failure metadata (organization/program name, report id, provider/failure code, timestamps) that already existed in `outbox_events`/`notification_deliveries`/`payment_attempts` but had no reader at all before this slice — never report content, never financial figures. Exactly one mutation exists, `replay_dead_lettered_outbox_event`, safe specifically because it reuses the unmodified `claim_outbox_events`/`complete_outbox_event` machinery and `outbox_event_receipts`' existing idempotency guarantee; notification-delivery and payment failures remain read-only this slice because tracing the actual handler code showed no existing safe retry path for either (a permanently-failed notification's own outbox event has already reached `succeeded` by design). Live-verified: a full authorization matrix across eight identity types (only the platform admin succeeds), genuine cross-tenant visibility across two unrelated organizations, a genuine concurrent-replay race (exactly one winner, one clean rejection), and a full end-to-end recovery (a replayed event reprocessed by the real running worker, reaching `succeeded` with real reputation/notification fan-out). See `docs/decisions/0027-platform-operations-foundation.md`.
