# 0081 — Solvable CTF challenges + timed CTF events

## Status

Accepted. Two things, in order: (1) make every one of the 28 practice challenges genuinely
solvable by giving each a real static artifact; then (2) add timed CTF **events** on top of
that always-open practice library.

## Part 1 — the challenges were unsolvable

`app/ctf/[challengeId]/page.tsx` rendered a prompt ("A login page trusts a client-set
cookie… find the cookie… reach the admin panel") but there was **no artifact anywhere** to
derive the flag from — no file, no embedded data, no target. `submit_ctf_flag` (0072) was
correct; the gap was entirely upstream: nothing gave the researcher what they needed.

Fix: every challenge gets a real static artifact (decision #3 from the task: files or
embedded data only, never a live target to attack).

- **web / crypto / reverse-engineering / binary-pwn** → embedded material on the page
  (`MockCtfChallenge.embeddedData`): a code/response snippet, cookie value, ciphertext, JWT,
  RSA key + ciphertext, disassembly/pseudocode listing, hex dump, or custom-VM bytecode +
  opcode table.
- **forensics / network** → downloadable files (`MockCtfChallenge.artifacts`, served
  statically from `public/ctf-artifacts/<id>/`): a real JPEG with data after its EOI marker,
  a carvable disk image, a memory-dump blob, and real `.pcap` captures.

The artifacts are generated by `scripts/ctf-artifacts/` (`npm run ctf:artifacts`), which also
carries a **solver per challenge** and a `--verify` mode: it re-derives every flag from the
artifact it just produced and asserts it equals the plaintext whose sha256 the 0072 migration
seeds. All 28 verified, and the 28 computed hashes were confirmed byte-identical to the live
`ctf_challenges.flag_hash` column. The plaintext flags live only in the generator (build
time) and, hashed, in the migration — never in app code (`lib/mock/ctf.ts` still has no
`flag` field, per 0072) and never in the manifest the app imports.

### Substitution (disclosed)

Reverse-engineering and binary-pwn challenges would ideally ship a real compiled/attackable
binary. Building and hosting one is out of scope and unsafe in this repo's tooling, and a
live attack target is explicitly ruled out (decision #3). They ship a faithful static
substitute instead — an annotated disassembly / pseudocode listing, a hex dump, or a custom-VM
bytecode listing — built so the described technique performed against the listing yields the
exact flag (the license checker's key is reconstructed from its `mov`-immediate bytes; the VM's
bytecode is actually executed by the solver; the packed payload is XOR-decoded with the key
from its own unpack stub). The pwn challenges additionally show the captured program output
of the intended exploit, since a static artifact cannot run the exploit itself.

## Part 2 — timed events

Events are additive: the 28 challenges remain an always-open practice library outside any
event; an event picks a subset of them, opens for a window, and has its own leaderboard.

Schema (`db/migrations/202609290001_ctf_events.sql`): `ctf_events` (slug, name, window,
status enum draft/scheduled/active/ended, created_by), `ctf_event_challenges` (join to
existing challenges — never duplicated), and `ctf_event_solves` (the attribution table).

### Leaderboard-attribution model (the real design choice)

A flag submitted for a challenge in an active event must (a) go through the **same**
`submit_ctf_flag` verification (not forked) and (b) count toward that event's leaderboard.

Chosen: a **separate `ctf_event_solves` table**, written at solve time for every open event
that includes the challenge — rather than an `event_id` column on `ctf_solves`. Reasons:

- `ctf_solves` has `unique(researcher_id, challenge_id)` (one solve per challenge ever). A
  challenge can belong to several events, and a challenge solved in practice must not be
  silently credited to an event it wasn't solved during. A single `event_id` column can't
  express "counts for A and B" and fights that unique constraint.
- The attribution table keeps the practice solve exactly what it was (the durable fact +
  reputation provenance) and layers a time-scoped event standing on top. `submit_ctf_flag` is
  redefined with **one appended step** — fan out an attribution row per open event — with the
  window check (`now()` within `[starts_at, ends_at)`) as what makes it time-scoped. No
  verification logic is duplicated.

**Tradeoff (disclosed in the migration header too):** attribution credits solves made *during*
the window only — exactly what a timed competition wants. It deliberately does **not**
retroactively credit a challenge a researcher already solved in practice before the event
opened. In a real CTF you must (re)capture the flag during the event.

The global `/ctf` practice leaderboard stays mock and is labelled "Practice ranking" with its
existing "Preview / not a real ranking" note; the **real, ranked** boards are the per-event
ones (`get_ctf_event_leaderboard`, aggregated from `ctf_event_solves`).

### Admin + UI

Platform-admin CRUD (`/platform/ctf-events`) follows the existing platform-admin conventions:
every RPC re-checks `private.is_platform_admin()` and writes a `platform.ctf_event_*`
audit_logs row. The `/ctf` page gains an **Events** tab (one hierarchy level = one nav
control: the tab row is the CTF section's sub-nav, and Events never duplicates a
sidebar destination). Event detail is `/ctf/events/[slug]`; a challenge is reachable from
both the practice library and an event, with the same solve mechanism.
