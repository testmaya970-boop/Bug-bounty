# 0008: Report submission — composed authorization, a frozen scope snapshot, and a shared (non-authorizing) matching primitive

Date: 2026-08-27
Status: Accepted

## Context

A report is a security claim: "I found this vulnerability affecting this target within this program." Its submission must compose three independent facts, all re-derived server-side — the caller is an active researcher for this program, this program currently accepts submissions, and this target is actually in scope — and, once accepted, must remain historically explainable even after the program's scope later changes.

## Report status starts at `NEW`, not a task-suggested `SUBMITTED` — because `DOMAIN.md` already says so

`DOMAIN.md`'s existing "Reports" section defines the lifecycle in full: `NEW, TRIAGING, NEEDS_INFORMATION, ACCEPTED, RESOLVED` plus terminal outcomes `DUPLICATE, INFORMATIVE, NOT_APPLICABLE, REJECTED`, and states "Researchers cannot change report state." `DOMAIN.md` wins over the task's own suggestion. There is no `DRAFT` state in that list, so this slice does not build draft persistence (task section 31) — submission is one deliberate action that creates a report directly at `new`. All eight states are implemented at the enum level (not inventing new ones, not silently dropping domain-specified ones), but this slice implements **no transition RPC at all** — triage is explicitly out of scope, so a report simply stays at `new` until a future slice adds transitions, the same "implement the full domain enum, defer the transitions" pattern `0005`/`0006` already established for programs and scope.

## Minimal field set — description carries what `DOMAIN.md`'s full list would otherwise spread across separate fields

`DOMAIN.md`'s Reports section lists title, classification, affected asset, description, impact, reproduction steps, evidence, severity/CVSS, status, comments, events, bounty, and resolution as things a report *can* include — that is the eventual shape of the whole Reports domain, not a mandate that every field exist at first submission. This slice implements exactly what the task's own section 30 scopes: **program (implicit from context), target, title, description**. `classification` (a vulnerability taxonomy) and `severity` are both deliberately deferred — the task explicitly forbids inventing a taxonomy, and severity's real distinction (researcher-proposed vs. organization-confirmed) only matters once triage exists to do the confirming; adding an unconfirmed column now would be answering a question this slice has no way to act on. `impact` and `reproduction steps` are not separate fields — the single `description` field is where a researcher writes the full narrative, exactly as report content is already treated elsewhere in this codebase (`DESIGN.md`: preserve researcher-supplied content faithfully, never silently transform it). `evidence` (attachments) is deferred per the task; nothing in this schema blocks adding an `attachment` table with a `report_id` FK later. `comments`, `bounty`, `resolution` are named out of scope by the task itself.

## Report identifier

`reports.id` is a `gen_random_uuid()` primary key — the same non-sequential, non-enumerable identifier scheme every other table in this schema already uses. This already satisfies "non-sequential, public-safe identifier" without inventing a second identifier system, which the task explicitly said not to do without a real reason; there isn't one here.

## The composition problem this slice actually had to solve

`private.is_researcher_authorized_for_program` and `public.evaluate_program_scope` (`0006`/`0007`) are the two existing primitives the task named to compose. But `evaluate_program_scope` is authorized identically to every other scope operation — organization Owner/Security Admin, or a `program_members` manager — **deliberately not researcher-facing** (`0006`'s own words). A researcher calling it directly gets `FORBIDDEN`. Since `auth.uid()` reflects the original caller regardless of which `SECURITY DEFINER` function is currently executing (it reads session-level JWT claims, not the executing role), `submit_report` cannot simply call `public.evaluate_program_scope` internally on a researcher's behalf — that inner call would evaluate the *researcher's* authorization against the *manager* gate and fail.

The fix: the matching logic itself (which scope entry, if any, a canonical target resolves to) never needed to be manager-only — only *reading the result back out* does, since it can reveal private scope configuration to someone who shouldn't see it. So the matching SQL is now factored into `private.match_program_scope(...)`, a non-authorizing helper — it trusts its caller to have already decided who may see or act on the result, exactly like every other `private` function in this schema trusts the RLS policy or RPC that invokes it. `public.evaluate_program_scope` (redefined in this migration, not duplicated) now authorizes as a manager, then calls this shared helper; `public.submit_report` authorizes as a researcher (`is_researcher_authorized_for_program`), then calls the *same* helper. One matching implementation, two independently correct authorization gates in front of it — exactly the "compose, don't merge" structure the task asked for, and exactly the reason `0006`'s domain/URL/IP-CIDR matching logic did not have to be reimplemented or copy-pasted a third time.

`private.match_program_scope` is explicitly documented in its own migration comment as **not self-authorizing** — the one deliberate exception to every other `private` helper in this schema, which is worth flagging precisely because it is a deviation from the established pattern, not an oversight of it.

## Scope snapshot: both a reference and a frozen decision (option C)

A report stores: `asset_type`, `target` (canonical), `display_target` (as typed), `matched_scope_entry_id` (FK, `on delete set null`), `matched_scope_state`, and `matched_target` (the scope entry's own target string at match time). The FK lets an operator navigate to the scope entry's *current* state if it still exists; the snapshot fields freeze what was actually true *at submission time*, immune to the entry later being edited or soft-removed. This directly answers the day-1/day-2 scenario the task posed: a report accepted against `example.com` while it was in scope remains a valid, fully-explainable historical record even after `example.com` is later removed from scope — nothing re-evaluates it, and nothing needs to, because the acceptance decision was frozen at the moment it was made, not re-derived from current state on every read. `matched_scope_state` on a *successfully created* report is always `in_scope` by construction (an `out_of_scope` or no-match result blocks creation entirely — see below) — stored anyway, not because it could currently vary, but because a frozen record should say what was true, not require the reader to infer it from the fact that creation succeeded at all.

## The submission gate

`FORBIDDEN` (not authorized) → `SUBMISSIONS_CLOSED` (program not currently accepting reports) → validate title/description → `TARGET_NOT_ELIGIBLE` (no match, or an explicit `out_of_scope` match) → create. The last error is deliberately identical for "no scope entry matches at all" and "a scope entry matches but explicitly excludes it" — the task named this exact enumeration risk ("do not tell the researcher they almost matched internal target X"), and collapsing both into one generic, safe message closes it structurally rather than relying on care at every call site.

## Program lifecycle interaction — a real, testable rule, not a copy of `0007`'s full bypass

Scope mutation is gated to `draft` only (`0006`). Researcher invitation (`0007`) is not lifecycle-gated at all, because no status-transition RPC exists yet and gating it would have made the entire capability permanently unreachable. Report submission uses a middle position: **blocked only when `program.status in ('paused', 'closed')`**, allowed otherwise (`draft`, `review`, `active` — currently only `draft` is reachable, so this does not repeat `0007`'s all-or-nothing bind). This is a real, enforced, and independently testable rule (verified live by forcing a program to `paused`/`closed` via `service_role`, exactly as `0006`'s draft-lock was verified) rather than a deferred no-op, because "a paused or closed program must not silently accept reports" is self-evidently correct regardless of whether `active` is reachable yet, while "should a still-being-configured `draft` program accept reports" is a genuinely open question the task told this slice not to invent an answer to. Whether `draft` should also block submission is exactly the kind of rule a future lifecycle-transition slice should revisit, flagged here rather than silently decided.

## `list_my_reports`: the same profile-embed lesson from `0007`, applied before it could recur

A researcher can already read their own `reports` rows directly via RLS, but embedding the program/organization name through a normal PostgREST query would silently resolve to `null` once that researcher is no longer an *active* participant (suspended, or revoked) — the identical class of gap `0007` found live in the manager-facing roster's profile embed. Rather than wait to rediscover it, `list_my_reports()` is a `SECURITY DEFINER` function scoped to `auth.uid()`'s own reports, the same pattern `list_my_program_participations` already established, so a researcher's own report history remains fully readable regardless of their current participation status.

## Confidentiality / RLS

A report is readable by the researcher who submitted it, an organization Owner/Security Admin (oversight), or a `program_members` manager of that specific program — the identical three-way shape `programs`/`program_scope_entries` already use, extended with `researcher_id = auth.uid()` as the researcher's own path (analogous to, but narrower than, a manager's program-wide visibility: a researcher sees only their *own* reports, never another researcher's, even within the same program). An organization member without program-management standing (e.g., a `triager`-role org member not assigned to this specific program) sees nothing, matching the task's explicit "organization membership alone must not automatically expose reports" requirement. No insert/update/delete policy exists on `reports` — `submit_report` is the only writer, the same service-only boundary every table in this schema uses.

## Concurrency and the scope-change race

`submit_report` is one function call, one transaction, one un-locked `SELECT` against `program_scope_entries` immediately followed by the `INSERT`. Under Postgres's default `READ COMMITTED` isolation, this is fully deterministic without any explicit locking: whichever of the two concurrent transactions (a report submission's scope-match read, or a scope removal's `UPDATE`) *commits* first is what the other one's next statement observes — there is no window where the report's own `INSERT` could depend on a change that happens after that `SELECT` already ran. Verified live under genuine concurrency (see the engineering report).

## Deferred, explicitly

- Triage transitions, severity/classification, comments, bounty, attachments, notifications, public disclosure, AI analysis — all named out of scope by the task.
- A `draft` report state — `DOMAIN.md` does not define one.
- Duplicate-submission prevention beyond what the domain already requires (none) — two researchers, or the same researcher twice, may legitimately submit independent reports against the same target; deduplication is a triage-system decision, not a database constraint this slice should invent.
