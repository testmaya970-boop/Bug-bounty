# 0019: Public onboarding abuse hardening — invitations and evidence upload

Date: 2026-08-29
Status: Accepted

## Context

0018's production-hardening audit named three concrete, unaddressed abuse risks that matter specifically before opening researcher onboarding to the public: organization invitations, program/researcher invitations, and binary evidence upload all had no rate limit. This slice closes exactly those three, reusing the Postgres-backed `private.check_and_consume_rate_limit` primitive 0018 already built and live-verified — no second mechanism, no new table, no Redis.

## Determining the limits (not guessed)

Inspected actual product behavior before choosing numbers:

- **Organization invitations**: a legitimate owner/security_admin's real usage pattern is bursty at two points — onboarding a new organization (inviting an initial team, plausibly 5–20 people in one sitting) and occasional one-off additions afterward. Sustained hourly invitation-sending is not a real workflow.
- **Program/researcher invitations**: identical shape — a program manager builds an initial researcher roster at launch, then invites occasionally. The existing `organization_invitations_pending_unique`/`program_invitations_pending_unique` indexes already prevent the narrower "repeatedly invite the same address" abuse (destination-level); what was missing is a cap on total invitation volume from one actor (actor-level).
- **Evidence upload**: a researcher actively documenting a vulnerability might attach several files (screenshots, a PoC script, logs) per report in one sitting — realistically single digits, rarely more than a handful per report. A very active researcher working multiple reports in a burst could plausibly reach into the teens within an hour. Each attempt is materially more expensive than an invitation (up to 10 MiB of storage I/O), so the abuse cost per attempt is higher.

**Chosen limits: 20 per hour, keyed by the server-derived actor, for all three.** A single consistent number across all three was deliberately chosen over three independently-tuned ones: all three actions have the same shape (a burst-then-occasional legitimate pattern, no real workflow needing sustained high-frequency use), and one easy-to-explain number is easier to reason about and re-tune later than three arbitrary-looking ones. 20/hour comfortably covers the bursty-onboarding case identified above (a team of 20, a full initial researcher roster, a dozen-plus evidence attachments in one active session) while bounding sustained automated abuse to a small, fixed rate. These are documented initial values expected to need operational tuning with real usage data, not asserted as scientifically optimal — the goal is "legitimate workflow remains fast, automated abuse becomes expensive," not "strictest possible."

**Keying decision**: actor-only (the inviting/uploading user's own id), not organization/program/IP. Considered and deferred: an organization-wide aggregate cap (bounding total invitations sent by *any* admin of one organization, closing a multi-admin-collusion scenario) and an IP-based component (closing a single-actor-many-accounts scenario). Both are real, if lower-probability, gaps — deferred because the task explicitly warns against "an expensive quota system unless actual product behavior requires it," and actor-level keying alone already closes the concrete, named risk (one compromised or malicious account spamming invitations/uploads) without needing multi-dimensional bucket math before any real abuse pattern has been observed.

## Organization invitations

`invite_organization_member` redefined — every prior line (the owner-inviting-owner restriction, the insert, the audit log, and, critically, the pre-existing `organization_invitations_pending_unique` destination-level guard) unchanged. One check added immediately after `AUTH_REQUIRED`, keyed by `'org_invite:' || actor::text`, 20/hour, raising a distinct `RATE_LIMITED` error (SQLSTATE `53400`, the same custom code 0018 established) — placed at the identical position `submit_report`/`create_organization` already use, for consistency rather than inventing a new placement. **Actor-level vs. destination-level, explicitly distinguished and verified live**: the pre-existing unique index still independently rejects a second invitation to the *same* email (`INVITATION_PENDING`, `23505`) — a completely different error, proving the two controls operate independently rather than one masking the other. No plaintext token is ever logged by this change (nothing in this migration or the surrounding TypeScript service touches logging at all).

## Program / researcher invitations

`invite_researcher_to_program` redefined identically — keyed by `'program_invite:' || actor::text`, same limit, same position, every prior authorization/insert/audit line unchanged, the pre-existing `program_invitations_pending_unique` destination-level guard untouched. **Verified independently from acceptance**: this slice protects invitation *creation* only; `accept_program_invitation`/`accept_program_invitation_by_id` are untouched, since acceptance already has its own, separate authorization model (the accepting account's email must equal the invitation's email) that has nothing to do with the inviter's rate limit.

## Evidence upload

**Deliberately not folded into `add_researcher_file_evidence`/`add_organization_file_evidence`.** The existing upload flow (`services/report-file-evidence.ts`) writes bytes to storage *before* calling either finalize RPC (0011's bytes-then-row invariant, unchanged) — checking the limit only inside the finalize RPC would reject a request only *after* the expensive storage write the limit exists to prevent had already happened, exactly the ordering this task requires avoiding. Instead: a new, standalone `public.check_evidence_upload_rate_limit()` RPC (`security definer`, re-deriving `auth.uid()` itself, keyed by `'evidence_upload:' || actor::text`, 20/hour) is called by the TypeScript service **first** — after cheap, local, zero-I/O `validate(input)` (filename/size checks), but strictly before the SHA-256 hash computation, the storage `putObject` call, and the finalize RPC. Verified via a dedicated unit test (`report-file-evidence-service.test.ts`, "the upload rate limit is checked BEFORE any storage write, never after") that `evidenceObjectStore.putObject` is never invoked when the rate-limit check returns `false` — a direct assertion on the real function's control flow, not a live storage test (see "What was and wasn't live-tested" below).

## Fail-open / fail-closed, decided per action, not globally

0018's rate limiter fails open on an infrastructure error (an RPC error checking the limit does not itself block the action) for **sign-in** specifically, reasoned there as: sign-in is the one gateway to everything else in the product, so a limiter outage must never lock out every legitimate user platform-wide. This slice does **not** change that global default, and re-examined the question independently for each of the three newly-protected actions:

- **Organization/program invitations**: the rate-limit check is one line *inside* the same transaction as the mutation itself (identical to `submit_report`/`create_organization`). There is no separate "limiter call" distinct from "the RPC call" — an infrastructure error here behaves exactly like an infrastructure error anywhere else in an existing RPC (the whole call fails, the client sees a mapped `UNKNOWN`, nothing partial commits). This is not a new fail-open/fail-closed decision requiring its own reasoning; it is the same behavior every existing RPC in this schema already has for any unexpected failure.
- **Evidence upload**: this **is** a genuinely separate network call (the pre-check RPC), and a deliberate, scoped choice was made: **fail closed** — `services/report-file-evidence.ts` treats an RPC-level error from `check_evidence_upload_rate_limit` as blocking the upload (mapped through the existing `mapRpcError`), not as "assume allowed." This is the opposite of sign-in's choice, for a concrete reason: evidence upload is one incremental action within an already-reachable, already-in-progress workflow (unlike sign-in, which gates *everything*) — a temporary block during a rate-limiter hiccup leaves the researcher able to do everything else (view/discuss the report, retry shortly), while the abuse this limit guards against (storage cost, asymmetric — an attacker's attempt costs them little but costs Sentinel real storage) justifies erring toward caution specifically here, unlike a failed sign-in attempt which costs the attacker time, not Sentinel resources. Verified via a dedicated unit test.

## Concurrency

Genuine concurrency (`Start-Job`-backed, truly parallel HTTP requests, not sequential) was tested for all three protected actions independently, each against a fresh actor with a clean rate-limit window: 25 concurrent calls against the 20/hour limit produced **exactly 20** successes in every case — organization invitation, program invitation, and the evidence-upload rate-limit check. This is the same atomic-upsert primitive 0018 already proved race-safe; re-verifying it under each new bucket-key pattern (rather than assuming the prior proof transfers) confirmed no per-action wiring mistake introduced a race.

## Tenant isolation

Verified live: organization A's owner exhausting their own 20/hour invitation budget had zero effect on organization B's owner, who successfully sent an invitation immediately afterward — the bucket key is the actor's own id, never a client-supplied organization/program id, so cross-tenant quota consumption is structurally impossible (two different people always get two different buckets). The one scenario where budget *is* deliberately shared — the same person acting as owner of two different organizations — is an accepted, reasoned design choice (bounding the *person's* total activity, not the organization's), not a tenant-isolation bug, and is documented as such above under "Determining the limits."

## Storage ordering

The invariant — a rejected/rate-limited request must not create a storage object — is enforced by the code path itself (the rate-limit check is a prerequisite `await` before `evidenceObjectStore.putObject` is ever reached) and confirmed by a direct unit-test assertion that `putObject` is never called when the check returns `false`. **What was and wasn't live-tested**: the rate-limit *mechanism* (the SQL RPC itself — boundary success, first rejection, concurrency, tenant isolation, anonymous/unauthorized rejection) was verified against real PostgreSQL exactly as thoroughly as the other two protected actions. A full end-to-end live test of the *actual* TypeScript upload path against a real Supabase Storage bucket was not performed this slice: `services/report-file-evidence.ts` depends on `createSupabaseServerClient()`, which reads Next.js's request-scoped cookies via `next/headers` and has no meaning outside an actual Next.js request (the same constraint that applies to every service in this codebase, not something specific to this change) — exercising it end to end would require a running Next.js server and a real authenticated browser session, judged out of proportion to this narrowly-scoped slice. The ordering invariant is therefore proven at two levels that together give high confidence — the real database mechanism, and a direct assertion on the real TypeScript control flow — but not via one single end-to-end live request.

## Error contract

No second error format was introduced. `RATE_LIMITED` flows through the exact same `mapRpcError`/`OrganizationServiceError` convention every other error in this codebase already uses; the API-side `lib/http-errors.ts` table already maps `RATE_LIMITED → 429` (added in 0018, unchanged here) — a client on the eventual frontend receives `{ code: "RATE_LIMITED", message: "Too many ... recently, try again later." }` (or, for evidence upload, "Too many uploads recently. Try again later." from the TypeScript service layer directly), never a SQLSTATE, a raw Postgres message, or any internal detail.

## 10× assessment

- **10× safer**: the limit is enforced in the database/service layer, unreachable from a client regardless of what the eventual UI does or doesn't disable.
- **10× cheaper**: zero new infrastructure — the exact same table and function 0018 already built.
- **10× scalable**: the same atomic upsert, proven race-safe under genuine concurrent load for all three new bucket-key patterns.
- **10× better UX**: 20/hour comfortably covers every legitimate burst pattern identified (team onboarding, researcher-roster building, multi-file evidence attachment) without ever being felt by a normal user.
- **10× maintainable**: one rate-limit contract (`private.check_and_consume_rate_limit`), now applied to six total actions (sign-in, report submission, organization creation, organization invitation, program invitation, evidence upload) across three different call-site shapes (embedded-in-mutation-RPC, pre-auth public wrapper, pre-storage-write public wrapper) — a template every future abuse-sensitive action can follow.

## Deferred, explicitly

Organization/program-wide aggregate invitation caps (bounding multiple admins of one organization collectively, not just one actor), an IP-based component, quotas/billing limits/subscription tiers/plans, usage dashboards, admin controls for adjusting limits, analytics, any notification change, API expansion, and payment providers — none of it built, all of it out of this narrowly-scoped slice's stated boundaries.
