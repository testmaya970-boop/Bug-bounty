# 0052.1 — Email delivery audit: local vs. production, honest UI, resend

Related: [[0052-account-security-mfa-sessions-email-verification]].

## The actual root cause

Reproduced live with a fresh account, per the required chain (signup → auth.users row →
email_confirmed_at → SMTP → Mailpit → inbox → confirm link → verified session). Every
step of the technical chain worked correctly on inspection. The real issue was that
`supabase/config.toml`'s `[auth.email.smtp]` (production SMTP) is entirely commented out
-- confirmed by reading the file, not assumed -- so local Unpatched signup **cannot**
deliver to a real external inbox; it intentionally terminates in Mailpit
(`[local_smtp]`, port 54324). The "Check your email" screen never disclosed this, so a
real Mailpit-only test read as "no email arrives."

## 1. Reproduction (fresh account, full chain recorded)

- Signup response: real, no error.
- `auth.users` row created; `email_confirmed_at` / `confirmed_at`: both `null` (correct --
  unconfirmed).
- Mailpit message count for the address: **1**.
- Recipient: exact match.
- Subject: "Confirm your Unpatched account."
- Confirmation URL inside the actual email:
  `http://127.0.0.1:3000/auth/confirm?token_hash=pkce_...&type=signup` -- Unpatched's own
  route, real token, correct type, **no hardcoded `next=/organizations`** after this
  slice's fix (see below).
- Following the link in Chromium: unverified → confirmed → real session → correct
  researcher destination (`/programs`).

One discrepancy from the bug report: the report's screenshot showed "We sent a
confirmation link to . Follow it..." with a **blank** email address. A fresh reproduction
this slice never showed a blank address -- `signUpWithPassword` always returns the literal
email argument it was given, with no code path that could empty it. Flagged, not silently
assumed away: possibly a copy/paste artifact in the original report, or a state I could
not reproduce. Not treated as fixed, because it was never confirmed broken.

## 2. Local vs. real email delivery -- stated explicitly, not guessed

**Local development: Supabase Auth → `local_smtp` → Mailpit. It stops there.** A local
signup email never reaches a real inbox, by design -- this is Supabase's own standard
local dev architecture (previously Inbucket, now Mailpit), not a Unpatched-specific
shortcut. Confirmed by inspecting `supabase/config.toml` directly: `[local_smtp]
enabled = true` (port 54324, the Mailpit web UI); `[auth.email.smtp]` is fully commented
out, with only a template for a real provider (`smtp.sendgrid.net`) left as an example.

**Production readiness: cannot be verified from this environment.** No SMTP
host/user/password/API key is configured anywhere in this repository -- `.env.local`,
`supabase/config.toml`, and the codebase were all checked. Wiring a real provider (the
commented `[auth.email.smtp]` block, or `docs/decisions/0022-real-email-provider-
integration.md`'s own transactional-email design for in-app notifications, a separate
system from Supabase Auth's own mailer) is a deployment-time configuration step, not
something this slice can build or verify without real credentials. Stating this plainly
rather than claiming delivery "works" because Mailpit captured a message.

`components/auth/confirm-email-pending.tsx` (new): the "Check your email" screen now
conditionally shows a **"Local development"** notice with a real, direct link to Mailpit
(`http://127.0.0.1:54324`) -- rendered only when `isLocalSupabaseEnvironment()` (new,
`lib/env.ts`) is genuinely true, a real check of the app's own configured

a production `NEXT_PUBLIC_SUPABASE_URL` provably never shows it.

Email content verified directly from the real Mailpit message (not assumed): correct
recipient, correct "Unpatched" branding/subject, a real (not localhost-in-production --
built from the request's own host header, unchanged since 0023) confirmation URL, no
malformed URL, no unsafe redirect (`safePath` guard unchanged).

## 5. A real, previously-undiscovered bug: intent collapsed for every real confirmation

The confirmation email template (`supabase/templates/confirmation.html`) hardcoded
`next=/organizations` into every link, which silently defeated 0052's own
intent-aware, organization-auto-creating redirect logic in `/auth/confirm` for every real
(non-immediate) signup confirmation -- both researcher and organization signups were
landing on `/organizations` regardless of what they'd chosen. This was only reachable
once `enable_confirmations` was actually turned on in 0052; caught live this slice by
reproducing a researcher signup end to end and watching it land on the wrong page.
**Fixed**: removed the hardcoded `next` from the template; re-verified live for both
intents:

- Researcher: confirm → real session → **`/programs`**.
- Organization: confirm → real session → organization **actually auto-created** with the
  entered name → **`/organizations/{id}/members`**.

Template edits required an auth-container restart to take effect (`docker restart
supabase_auth_...`) -- config/template changes are not picked up by `supabase db reset`
alone, confirmed live after an initial false-negative retest.

## 6. Resend confirmation -- audited (did not exist), then built

No resend capability existed anywhere in the codebase before this slice (`grep` across
`actions/`/`services/` for "resend," confirmed empty). Built on Supabase Auth's own native
`auth.resend({ type: "signup", email })` -- never a second, custom OTP system.

**Enumeration safety verified live**, not assumed: calling resend for a real unconfirmed
account, a fabricated nonexistent address, and an already-confirmed account all returned
the byte-identical `{ error: null }`. `resendConfirmationEmailAction` preserves this: only
a genuine rate-limit error is ever distinguishable from success, the same contract
`requestPasswordResetAction` (0023) already established.

**Rate limiting is real, not decorative**: an immediate second resend for the same address
returns Supabase's own real cooldown error (mapped to `RATE_LIMITED`); waiting a few
seconds and retrying delivers a genuine second email, confirmed via Mailpit message count
going from 1 to 2. The client also shows a 30-second cooldown on the button itself
(UX politeness layered on top of the real server-side boundary, never a substitute for it).

Two real surfaces added: `ConfirmEmailPending`'s "Didn't receive it?" button (right after
signup, knows the email already), and `SignInForm`'s inline resend button that appears
specifically when sign-in fails with `EMAIL_NOT_CONFIRMED` (the account owner just proved
they know the password, so offering resend there is the single most useful place after
the confirm-pending screen itself).

## 7. Auth security posture -- unchanged, re-verified

Safe redirects (`isSafeRedirect`, unchanged), enumeration-safe errors (extended, not
weakened, to resend), SSR cookie handling (unchanged -- the confirm route's own
same-object-mutation fix from 0052 was preserved, not touched), rate limiting (real,
Supabase-native), MFA (untouched by this slice; full regression suite re-run), session
management (untouched), researcher/org intent routing (fixed, not weakened -- see #5).
