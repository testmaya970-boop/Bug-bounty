# 0010: Report evidence and communication — two tables, one visibility axis, no chat

Date: 2026-08-27
Status: Accepted

## Message vs. evidence: two different questions, two different tables

A communication answers "what does one party need to tell the other?" Evidence answers "what material supports the security claim?" These are genuinely different domain concepts — `DOMAIN.md`'s own Reports field list names both `comments` and `evidence` separately, alongside `description`/`impact`/`reproduction steps` (already folded into the single `description` field per `0008`) and `resolution` (a `reports`-level current-state field per `0009`). Collapsing communication and evidence into one generic `comments` table would erase that distinction and make "is this a message or a supporting artifact" an application-layer convention instead of a database-enforced one. This slice implements two tables: `report_messages` (communication) and `report_evidence` (supporting material), sharing a visibility model but never merged.

## The original report is never rewritten

`reports.title`/`description`/`target`/`researcher_id`/`submitted_at`/the scope snapshot are untouched by this slice. Every new communication/evidence item is an additional, independently-timestamped row referencing the report, never an edit to it — the report detail page's existing "Researcher submission" card (`0009`) is completely unmodified by this migration.

## Visibility: `researcher_visible` / `internal` — a considered default, `DOMAIN.md` names no taxonomy

`DOMAIN.md` does not name a visibility enum for report sub-records. Two values are the minimum the domain actually needs, and DESIGN.md's own confidentiality language ("private program existence must not be disclosed," "internal action metadata may be sensitive") already implies exactly this binary: something either reaches the researcher, or it stays internal to the organization. `public.report_visibility` enum: `'researcher_visible'` (both the submitting researcher and the organization can read it) and `'internal'` (organization only — owner/security_admin oversight or the program's own managers). A researcher-authored item is always `researcher_visible` by construction — the researcher-facing RPCs hardcode it, never accept a visibility parameter — because "internal" is an organization-only concept a researcher has no reason or path to produce. An organization-authored item may choose either value, the one place visibility is genuinely client-supplied, and only the enum's two values are possible (a `check`-constrained column type, not free text).

## Author context: derived, never trusted from the client

Both tables carry `author_context` (`'researcher'` | `'organization'`), computed server-side by comparing the authenticated actor to `reports.researcher_id` at insert time, never accepted as a parameter — the same "actor derived from `auth.uid()`, never trusted from the client" discipline every prior migration in this schema follows. This is what lets the UI render "Researcher" vs. "Organization" without re-deriving the relationship from role tables on every read.

## Two authorization paths, reusing the existing capability model, not inventing one

Researcher-authored content: `report.researcher_id = auth.uid()` and `private.is_researcher_authorized_for_program(report.program_id)` — the identical shape `submit_report` (`0008`) and the original `respond_to_information_request` (`0009`) already used. Organization-authored content: the same two-path manager check every program-management mutation uses (`has_org_role(['owner','security_admin'])` or `is_program_member`). No new capability framework, no new role, no invented permission — Billing Admin, non-members, cross-program, and cross-tenant actors are rejected by the exact same predicate that already rejects them everywhere else in this codebase.

## A second, non-locking authorize helper — deliberately not reusing `0009`'s locking one

`private.lock_and_authorize_report_for_triage` (`0009`) takes `SELECT ... FOR UPDATE` because it protects an actual state mutation from a lost-update race. Posting a message or adding evidence is a pure append with no read-modify-write on the report row itself — locking it would only serialize unrelated concurrent communication for no correctness benefit. This slice adds `private.authorize_report_for_communication`, structurally identical to the `0009` helper (derive actor, locate the report, authorize, return it) but with a plain `SELECT`, not `FOR UPDATE`. The two-line authorization predicate (`has_org_role`/`is_program_member`) is duplicated between the two helpers rather than factored into one shared function — the same acceptable duplication `0006`'s `add_scope_entry`/`update_scope_entry`/`remove_scope_entry` already inline independently; the migration files this slice must not retroactively edit (`0009`) are left untouched.

## Superseding the one-shot fields, not running two competing systems

`reports.information_request_reason` and `reports.researcher_response` (`0009`) are **dropped** in this migration and replaced by `report_messages` rows. Keeping both would mean two places a request or a response could live, and `0009`'s own reasoning for why a second history table was unnecessary — "audit already covers what happened, current-state columns cover what's true now" — argued against exactly this kind of duplication once a real communication model exists to own it properly. `resolve_report`'s `resolution_summary` is **not** touched — it is not a conversational exchange, it is a `DOMAIN.md`-named current-state fact about the report's own resolution, the same category as `confirmed_severity`/`duplicate_of_report_id`, and stays a `reports` column.

`request_information(report_id, reason)` is **redefined** (same signature, same status-transition behavior, same `report.information_requested` audit event) to write the reason into a `report_messages` row via `private.insert_report_message` instead of a column. `respond_to_information_request` is **dropped** and replaced by `post_researcher_message` — communication is no longer gated to `status = 'needs_information'`; a researcher may add a researcher-visible message or evidence to their own report at any time their participation is active, matching how organizations may too. This is a deliberate loosening from `0009`'s one-shot field, justified because "communication is supporting data, not itself a state transition" (this task's own framing) — gating it to one specific status was only ever a side effect of it living on the state-transition RPC in the first place, not a domain requirement. `DOMAIN.md` never restricted *when* comments may be added, only that researchers cannot change report *state* — which remains exactly as true here as before: no message or evidence insert touches `reports.status`.

## No hidden coupling between communication and state

`post_researcher_message`, `post_organization_message`, `add_researcher_evidence`, and `add_organization_evidence` never write to `reports.status`. `request_information` is the one place a message and a transition happen together, and it does so as one explicit, named, already-audited domain operation — not because inserting a message secretly triggers anything.

## Database model: two tables, a real composite tie to the report, no JSON escape hatch

`report_messages` and `report_evidence` both carry `report_id`, `program_id`, `organization_id` (denormalized, tied together by one composite foreign key to a new `reports(id, program_id, organization_id)` unique constraint — the same "child row can never disagree with its parent's tenant" pattern `program_scope_entries`/`program_members` already established) plus `researcher_id` (copied server-side from the located report row inside the same transaction, never independently client-supplied, so no separate constraint is needed to keep it honest). All core fields are typed columns — `author_context`, `visibility`, `evidence_type` are real enums, not a generic `metadata jsonb` escape hatch. `report_evidence.evidence_type` is one of `text`, `code`, `url`, `log` — non-binary, matching the task's explicit "smallest useful evidence model" instruction; binary attachments are deferred (see below).

## Immutability and deletion: both tables are append-only, no update, no delete, in this slice

Security evidence and communication history should be trustworthy without needing a version history mechanism this slice doesn't otherwise need. No `UPDATE`/`DELETE` RPC exists for either table, and no RLS policy grants either operation to `authenticated` — the same "service-only, no direct client write" boundary the rest of this schema uses, taken one step further by omitting the mutation RPCs entirely. This is a deliberate, disclosed deferral (a future "retract evidence"/"edit message" capability would need its own audit-and-retention design), not an oversight — nothing in `DOMAIN.md` requires editing or deleting either concept yet, and the task's own guidance is explicit: if editing/deletion isn't needed, don't implement it.

## Audit

Every successful `post_researcher_message`/`post_organization_message`/`add_researcher_evidence`/`add_organization_evidence` call writes exactly one `audit_logs` row (`report.message_posted` / `report.evidence_added`), `entity_type = 'report'`, `entity_id = report_id` — deliberately the same `entity_type`/`entity_id` shape every other report-lifecycle audit event already uses, so the existing `getReportAuditActivity` read path (`0009`) picks up these new events with no service-layer change. `request_information` still writes exactly one event (`report.information_requested`), not two — the message row it also creates is the artifact of that one action, not a second auditable action. Communication/evidence rows themselves are never treated as the audit trail (`report_messages`/`report_evidence` answer "what did people say/attach"; `audit_logs` answers "what system action occurred") — the same distinction `0009` already drew between `reports.status` and `audit_logs`.

## Concurrency

Communication and evidence creation are pure appends with no row lock needed or taken — two genuinely concurrent messages (or two evidence adds, or one of each) on the same report both succeed, each its own row, each its own audit event. The one interaction that matters is `request_information` racing a plain message/evidence post: since posting never touches `reports.status` and `request_information` only locks the `reports` row (not `report_messages`/`report_evidence`), both complete independently and deterministically — the final database state is exactly the union of whichever committed, explainable by reading the rows, never a lost write or a phantom one.

## RLS

`report_messages`/`report_evidence` SELECT policy: `(visibility = 'researcher_visible' and researcher_id = auth.uid()) or has_org_role(organization_id, ['owner','security_admin']) or is_program_member(program_id)`. No insert/update/delete policy on either table — every write goes through the RPCs above, the same service-only pattern every table in this schema uses.

## A proactively-closed `public.users` read gap, found by design review — and a second, deeper bug caught inside that fix before it shipped

Embedding an author's display name on a message/evidence read (`author:users!author_id(display_name)`) exposed the identical class of bug `0007` and `0008` each found live once already: `public.users`' existing read policies are "self," "org co-members" (a researcher is never an org co-member of a manager, by design), and — since `0007`'s own fix — "a manager may read a researcher's profile." There was no reverse path: a researcher reading a message authored by a manager or an oversight-acting owner/security_admin would have silently resolved that author's name to null. Recognizing the pattern from its first two occurrences, this migration adds the symmetric policy before shipping rather than waiting to rediscover it live a third time.

The first attempt mirrored `0007`'s policy shape literally: an inline `exists()` subquery against `program_members`/`organization_members` directly inside the new `users` policy body. Live verification (`SET LOCAL request.jwt.claims` to simulate a researcher's session directly against Postgres, then evaluating the policy's own `exists()` expression by hand) caught a real, second bug before it shipped: the inline subquery is itself subject to `program_members`'/`organization_members`' *own* RLS, and a plain researcher has no RLS-permitted read path to either table at all — so the `exists()` always evaluated `false`, silently, regardless of whether the underlying relationship was real. `0007`'s original policy does not have this problem only because *its* querying actor (a manager) already has legitimate RLS read access to `program_researchers` via `has_org_role`/`is_program_member`; reversed, that assumption breaks. This is the identical RLS self-reference problem the `private` schema helper pattern exists to solve everywhere else in this codebase — the fix is the same one, applied here for the first time to a *cross-user* lookup: `private.is_manager_or_admin_of_my_program(candidate_user_id)`, a `SECURITY DEFINER` helper that bypasses `program_members`'/`organization_members`' RLS internally (the same way `private.has_org_role`/`private.is_program_member` already bypass their own tables' RLS for every other policy in this schema), self-authorizing the *caller* via `auth.uid()` while taking the *candidate* user id being asked about as its one parameter — a real, disclosed deviation from this schema's "no target-user parameter" helper convention, unavoidable here because the whole point is asking about a *different* user, bounded safely because the function is never exposed as a callable RPC and its own query is scoped to the caller's own actively-authorized programs (`pr.user_id = actor and pr.status = 'active'`), never an arbitrary program. Verified live (both the original bug and the fix) below.

## Attachments and binary evidence: deferred, with the architecture documented, not implemented

No Supabase Storage bucket, object-storage abstraction, or attachment table exists anywhere in this repository today (confirmed by inspection before writing this migration — `supabase/config.toml`'s `[storage]` block is the default local-dev scaffold, no bucket is configured). `SECURITY.md` requires, for whenever binary attachments are actually built: a private (non-public) bucket; a server-side authorization decision before every download, not a bare signed URL; randomized, non-guessable object keys (never a user-controlled or path-traversal-prone key); content-type verification independent of the client-supplied MIME type; a size limit; a malware-scanning architecture; and audited access where required. None of this is implemented here — implementing a partial version (e.g., checking a filename extension and calling it "secure") would be worse than not implementing it, per the task's explicit instruction. The `report_evidence` table's `evidence_type` enum is structured so a future `screenshot`/`file` value can be added additively, with its `content` column repurposed to hold an opaque storage-object reference rather than inline text, once that infrastructure exists — nothing in today's schema needs to change to make room for it.

## Deferred, explicitly

Binary/file attachments and the storage architecture above, message/evidence editing, message/evidence deletion or retraction, threaded replies, real-time delivery, reactions, read receipts, typing indicators, a generic comments API, bounty/payments/reputation/notifications/public disclosure/AI/search/analytics/integrations — all named out of scope by the task.
