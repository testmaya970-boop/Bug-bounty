# 0011: Binary evidence storage — a provider-independent object store, opaque keys, bytes-before-row consistency

Date: 2026-08-27
Status: Accepted

## Objective

Not "file upload." A secure evidence-storage *boundary* the domain can rely on regardless of which object-storage provider sits behind it. `0010` deferred binary evidence and documented the requirements this slice must satisfy: private storage, a server authorization decision before every download, randomized non-guessable object keys, no `dangerouslySetInnerHTML`-class rendering of file content, a documented (not necessarily automated) malware-scanning boundary, and no service-role credential ever reaching the browser.

## Provider: Supabase Storage, reached only through `lib/evidence-store.ts`

Inspected before building anything: `supabase/config.toml`'s `[storage]` block is the default local-dev scaffold (`enabled = true`, `file_size_limit = "50MiB"`, S3-protocol enabled) — no bucket, no attachment table, no storage-adjacent code existed anywhere in this repository (confirmed by search) before this migration. Supabase Storage is already running as part of the same local stack every other slice this session has verified against, needs no new infrastructure or fabricated credentials, and is a real S3-compatible object store (Supabase Storage's own backend), not a toy. It is used exclusively behind a small, explicit `EvidenceObjectStore` interface (`lib/evidence-store.ts`): `putObject`, `getSignedDownloadUrl`, `deleteObject` — nothing else, because nothing else is needed for this slice. No other file in the codebase imports `@supabase/supabase-js`'s `.storage` namespace or references a bucket name. The domain and database layers know only "evidence object," never "Supabase Storage object" — swapping to S3, R2, or self-hosted object storage later means writing one new file that implements the same three-function interface and changing one import, never touching `report_evidence`, its RLS, its RPCs, or any UI component.

## Object identity: server-generated, opaque, unguessable

Object keys are `evidence/<uuid>`, generated with Node's `crypto.randomUUID()` (a CSPRNG, not `Math.random()`) in the TypeScript orchestration layer — never the original filename, never derived from `organization_id`/`report_id`/`researcher_id`/any predictable value. A database check constraint (`report_evidence_object_key_format_check`) enforces the exact key shape at the schema level, so a malformed or attacker-influenced key can never be persisted regardless of what future code path might try to insert one.

## Database model: `report_evidence` gains a file shape, not a new table

`report_evidence_type` gains a fifth value, `'file'`. Five new nullable columns — `object_key`, `original_filename`, `content_type`, `size_bytes`, `sha256` — with a check constraint enforcing exactly one of two shapes per row: a `file` row has all five file fields populated and `content` null; every other type keeps `content` populated and every file field null. No `report_files`/`report_attachments` table, no generic JSON metadata blob — every field here is independently justified: `object_key` locates the bytes, `original_filename` is display-only untrusted metadata, `content_type` is stored-but-unvalidated metadata (see below), `size_bytes`/`sha256` are server-derived integrity facts. Everything else about a file evidence row — `report_id`/`program_id`/`organization_id`/`researcher_id` (the same composite-FK tie `0010` established), `author_id`/`author_context`, `visibility`, `created_at` — is identical to text/code/url/log evidence, because it is the *same domain concept* (evidence) with a different content shape, not a different concept.

## No `upload_status` column — a persisted row is, by construction, proof the upload succeeded

Object storage and PostgreSQL do not share one ACID transaction, so this slice cannot honestly claim "file bytes and the database row are written atomically." Two orderings were considered: insert-a-pending-row-then-upload, or upload-then-insert-the-row. This slice uses the second, and it is what removes the need for a status column at all: the object is written to the private bucket **before** any `report_evidence` row referencing it is ever inserted, and the insert only happens if the upload already succeeded. A `report_evidence` row of `evidence_type = 'file'` can therefore only ever exist in one state — "the object exists" — so a status column that could only ever hold one value would be exactly the kind of column nothing reads or branches on that this schema's discipline already rejects for `report_evidence.evidence_type`-adjacent concerns (compare `0009`'s identical reasoning for deferring `assignee`). This directly satisfies the core invariant the task named: *a database evidence record must never authorize access to an object that was never successfully uploaded* — it is true by construction, not by a status flag that could drift from reality.

## The failure mode this ordering does *not* solve, and its documented (not automated) mitigation

The reverse failure is possible: the object upload succeeds, but the subsequent RPC call that inserts the `report_evidence` row fails (a race where the actor's authorization changed between the pre-check and the finalize call, a network drop, a validation rejection). This leaves an orphaned object in storage with no referencing row — a real, disclosed gap, not hidden. Two mitigations: (1) the orchestration layer (`services/report-file-evidence.ts`) makes a best-effort `deleteObject` call immediately if the finalize RPC rejects after a successful upload — this closes the common case inline, not just in documentation; (2) for the residual case where even the cleanup call itself fails (e.g., the process crashes mid-flow), the defined-but-not-implemented strategy is: a future scheduled job lists objects under `evidence/` in the bucket, diffs against every `report_evidence.object_key`, and deletes any object with no matching row older than 24 hours (giving any in-flight legitimate upload time to finish). This slice does not ship that job — a foundation slice's job is to make the failure mode rare, bounded, and clearly defined, not to build a cron scheduler the task's own scope explicitly excludes.

## Upload authorization: the database is the sole boundary, exactly like every other evidence RPC

No TypeScript-side pre-check was added before the storage write — deliberately, to avoid a second, parallel authorization implementation that could drift from the real one (the same reasoning `services/authorization.ts` and every RPC in this schema already follow: one implementation, not two that must agree). `add_researcher_file_evidence` and `add_organization_file_evidence` re-derive the actor from `auth.uid()` and check authorization exactly like `0010`'s non-file evidence RPCs — no client-supplied `researcher_id`/`organization_id`/`program_id`/`actor_id`/`visibility`-for-a-researcher-caller can influence the outcome. A consequence, disclosed here rather than glossed over: because these RPCs cannot themselves verify against Supabase Storage that the referenced object actually exists (Postgres has no built-in way to query a separate HTTP service without additional extensions this slice does not add), a malicious *already-authorized* caller (an authenticated researcher on their own report, or an org manager on a report their organization already controls) could in principle call the RPC directly with a well-formed but fabricated `object_key`/`sha256`/`size_bytes`, creating a `report_evidence` row that claims an object that was never uploaded. This is bounded, not a privilege-escalation or cross-tenant issue — the caller must already hold exactly the authority needed to add real evidence to that same report, so the only outcome is a broken/junk evidence entry on a report they already control, and any later download attempt against a fabricated key fails cleanly (the signed-URL/download step below fails against a real, nonexistent object, it does not expose someone else's data). Flagged as a remaining risk, with a stronger mitigation described there rather than implemented now.

## Hashing: server-derived from the actual received bytes

SHA-256 is computed in the Server Action from the buffered upload bytes (Node's built-in `crypto.createHash('sha256')`), before the object is written to storage and before the hash is ever passed to the finalize RPC as a parameter. A client-supplied hash is never accepted or trusted anywhere in this flow. Deduplication by hash is not implemented — `DOMAIN.md` does not require it, and two researchers (or the same researcher) may legitimately submit independently-obtained copies of the same artifact; the hash exists for future integrity verification and forensic traceability, not as a dedup key today.

## Size limit: 10 MiB, chosen and documented, not arbitrary

Enforced server-side (`report_evidence_size_bytes_check`: `0 < size_bytes <= 10485760`) and independently in the orchestration layer before any storage write is attempted. 10 MiB comfortably covers the evidence shapes this slice actually needs to support well — screenshots, short logs, HAR/PCAP captures, small proof-of-concept scripts or binaries — without inviting the very different architecture (chunked/resumable upload, streaming) that large video evidence would require, and sits deliberately below the bucket's own `file_size_limit` (10 MiB app-level vs. Supabase Storage's local default of 50 MiB) so this application's own validation is what a user actually sees rejecting an oversized file, with a clear message, rather than a generic storage-layer error. The client-side limit shown in the UI is UX only; the server/storage boundary above is authoritative and was verified live by attempting to exceed it.

## Content type: stored as metadata, never trusted as proof of file type

The client-supplied MIME type is stored on `content_type` for informational display only. No magic-byte/content-sniffing validation is performed in this slice — this is stated plainly rather than implied by silence, per the task's explicit instruction not to falsely claim MIME validation that does not exist. The control that actually matters is on the download side, not the upload side: every download is forced to `Content-Disposition: attachment` (see below) regardless of what content type is stored, so a browser navigating directly to a download URL can never be tricked into rendering a maliciously-labeled file inline as HTML/SVG/script — this is the real defense against the "do not render uploaded HTML directly" requirement, not upload-time filtering.

## Download authorization: RLS decides, a short-lived signed URL delivers

No public bucket, no permanent URL, no signed-upload-token or storage credential of any kind reaches the browser. A download request re-reads the specific `report_evidence` row through the caller's own session-scoped Supabase client — the exact same RLS policy `0010` already established (`researcher_visible` + own report, or org oversight/program membership) is the authorization decision; a denied or nonexistent row is indistinguishable (`null`), the same confidentiality-safe shape every other read in this codebase already uses. Only once that read succeeds does the server-only service-role client generate a 60-second signed URL (`createSignedUrl(..., { download: originalFilename })`), which is what actually forces the attachment disposition regardless of stored content type. The browser is handed only that short-lived URL, never a bucket path, never a credential.

## Visibility

Reused unchanged from `0010` — `researcher_visible`/`internal`, the same enum, the same RLS predicate, applied identically to file-typed rows as to text/code/url/log rows. No new `public`/`private` boolean was invented.

## Immutability and deletion

No update path exists for any `report_evidence` row (file or otherwise) — this was already true after `0010` and remains true here. A corrected or re-taken piece of evidence is a new row with a new object key, never a replacement of existing bytes behind the same evidence id — this is what gives the evidence trail forensic integrity: an evidence id's bytes, once referenced by a persisted row, never change. No delete RPC exists for evidence records, consistent with `0010`'s "do not casually implement DELETE" reasoning, now explicitly reaffirmed for file evidence — a `report_evidence` row may become part of a triage decision's reasoning and must not be capable of silently disappearing or changing underneath it.

## Scanning: no scanner, no fake status, the future boundary stated explicitly

No malware/content scanner is built in this slice, and no `scan_status` column was added — adding one that could only ever read "unscanned" (since nothing scans) would be exactly the "fake scanned status" the task explicitly forbade, and a column nothing meaningfully branches on besides. The future scanning boundary is stated precisely instead: it belongs between the hash computation and the storage `putObject` call in `services/report-file-evidence.ts` — a future scanning service would receive the already-buffered, already-hashed bytes at that exact point, and only a clean result would allow the flow to proceed to `putObject`/the finalize RPC; a `quarantined`/`scan_status` column would be added at that time, not before. Until then, file evidence is downloadable immediately upon successful upload — the same trust boundary `0010`'s text/code/log evidence already has (arbitrary attacker-controlled content, never executed by Unpatched, always presented as inert data), extended to bytes instead of text. Actual execution risk is bounded by the download-side controls above (forced attachment disposition, no inline rendering, no preview) — this is the standard, honest "safe download, not safe execution" posture the task explicitly permitted for this slice.

## Content security

No file content is ever rendered inline, previewed, or passed through `dangerouslySetInnerHTML`. Archives are never unpacked or inspected server-side. A download is always a forced-attachment fetch of opaque bytes through a short-lived signed URL — this is the entire content-security posture for this slice, deliberately, because a "safe universal previewer" is explicitly out of scope.

## Audit

`report.evidence_added` (already established by `0010`) covers file-evidence creation unchanged — the same event, now additionally carrying `evidence_type: "file"` in its metadata; no new creation event was invented for a content-shape variant of an already-audited action. A new event, `report.evidence_downloaded`, is added specifically for file evidence, because a *download* is a materially different, security-relevant action a text/code/log evidence read never had (reading `report_evidence.content` through the normal RLS-scoped list is an ordinary, un-audited read, same as reading `reports.description`; but *generating a signed URL to retrieve bytes from private storage* is closer in kind to the already-audited mutations than to a page render) — recorded with the actor and the evidence id, never the file's bytes or its signed URL. Every successful signed-URL issuance writes exactly one such event, in the same request that authorizes it; a denied attempt (RLS returned no row) writes nothing, the same "failed authorization produces zero audit rows" invariant every other mutation in this schema already has.

## Deferred, explicitly

Automated malware/content scanning, an automated orphan-object cleanup job (strategy defined above, not scheduled), deduplication by hash, archive inspection, inline/format-specific preview, resumable/chunked upload for files larger than 10 MiB, and every capability the task itself named out of scope (bounty, payments, reputation, notifications, public disclosure, AI, advanced search, analytics, integrations, real-time chat).
