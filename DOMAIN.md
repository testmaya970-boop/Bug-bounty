# Unpatched Domain Model

## Actors and relationships

Core actors are Researcher, Organization, Organization Member, Program Manager, Triager, and Platform Administrator. The conceptual reporting path is:

```text
Researcher → Report → Program → Organization → Assets
```

The major domains are Identity, Organizations, Programs, Assets/Scope, Reports, Triage, Severity, Bounties/Payments, Reputation, Notifications, Audit, API/Webhooks, and Moderation. Details are introduced through independently reviewable vertical slices.

## Organization lifecycle

`CREATED → ACTIVE`. In practice organizations are created directly at `ACTIVE` — the `CREATED` state exists in the enum for a future review/provisioning step this slice doesn't need, not as a transient state creation currently passes through. Deletion is out of scope; a future `SUSPENDED`/`ARCHIVED` state is anticipated but not implemented, and nothing in the current schema or authorization model would need to change to add one later (status is already a proper enum column, not inferred from other state).

Creating an organization is a single atomic operation: it never exists without its owner, its owner is never assigned outside the same transaction as its creation, and the `organization.created` audit event is written in that same transaction. Any authenticated user can create an organization and becomes its owner — there is no approval step and no limit on how many organizations one user may create or own; nothing in this domain restricts it, and DOMAIN.md previously said nothing to the contrary. Slug is a normalized, server-generated internal identifier derived from the name, never a form field — routing is UUID-based, so the slug carries no product-facing meaning today.

## Organization membership

Organization-level authority and program-level access are different concepts and are never collapsed into one role field. An organization member has exactly one of five organization roles — Owner, Security Admin, Program Manager, Triager, Billing Admin — and each program membership (once programs exist) carries its own, separate program-level permissions. `services/authorization.ts` is the source of truth for what each organization role can and cannot do; UI copy is generated from it rather than hand-written, so it cannot drift from what the database enforces.

Member lifecycle states are `ACTIVE`, `SUSPENDED`, and `REMOVED`. There is deliberately no `INVITED` state on a membership row: a person cannot belong to an organization before they have an Unpatched account, so the pending phase between an invitation being sent and accepted is represented entirely by a row in `organization_invitations` (keyed by email), not by a membership row. Accepting an invitation is the transition that creates (or reactivates, if previously removed) the membership at `ACTIVE` — an invitee can do this either through the shared invitation link (proves nothing beyond "found the link") or from their own pending-invitations list once signed in; both paths require the accepting account's authenticated email to equal the invitation's email, so neither is a weaker authorization boundary than the other. Declining an invitation reuses the same admin-cancellation mechanism (`revoked_at`), since it is the same state transition from the invitee's side rather than a distinct domain concept. An organization must always retain at least one active Owner; the database enforces this transactionally on every role change, suspension, and removal, not only in the UI.

## Programs

The architecture supports public, private, invite-only, and vulnerability disclosure programs. Their lifecycle is `DRAFT → REVIEW → ACTIVE → PAUSED → CLOSED`; permitted transitions are implemented server-side with authorization and audit events (`submit_program_for_review`, `activate_program`, `pause_program`, `resume_program`, `close_program` — see `docs/decisions/0021-program-lifecycle-transitions.md`). `CLOSED` is terminal — no exit transition exists, mirroring this document's own report-lifecycle precedent.

A Program always belongs to exactly one Organization (`organization_id` is not null; there is no global program) and is created directly at `DRAFT` — creation never implies public visibility, researcher eligibility, or report eligibility. Only an organization Owner or Security Admin may create one; the creator is added to a separate, program-scoped `program_members` table with the program-level role `manager` in the same transaction as creation — this is deliberately **not** the same concept as the organization-level `program_manager` role: per this document's own "Organization membership" section, organization-level authority and program-level access are different concepts and are never collapsed into one role field. An organization member holding the org-level `program_manager` role gets no automatic access to any program; access comes from an explicit `program_members` row, or from an Owner/Security Admin's organization-wide oversight. The identical two-path authorization also governs every lifecycle transition. See `docs/decisions/0004-program-authorization.md` for the full authorization model, including what is deliberately deferred (adding further program members beyond the creator, and program-level roles beyond `manager`).

## Scope and assets

Scope defines what a researcher may test — a Program's scope is a set of `program_scope_entries`, each one of three initial target types (`domain`, `url`, `ip_cidr`), scoped to exactly one program. Each entry points at an organization-wide **asset** (`public.assets`, one per organization + type + canonical target): an asset can be in several programs, keeps its history after it leaves scope, and every report pins the asset it was filed against at submission (Oct 2026, the HackerOne/Bugcrowd asset-inventory model). Every target is canonicalized and validated in exactly one place, the database, before it is ever stored or matched against — never trusted or reinterpreted from the client. For a given target being checked, the single most-specific matching active entry decides `IN_SCOPE`/`OUT_OF_SCOPE`; no match means not in scope (default-deny). An explicit `OUT_OF_SCOPE` entry always outranks a broader matching rule that would otherwise include it (e.g. `admin.example.com` marked `OUT_OF_SCOPE` overrides a matching `*.example.com` marked `IN_SCOPE`). Scope entries are never physically deleted — "remove" transitions a row to a `removed` status, preserving it for future report history. Scope can be edited in every program status except `review` (locked while the platform reviews a launch). See `docs/decisions/0006-scope-asset-model.md` for the full canonicalization rules, matching semantics, and what is deliberately deferred (IDN/punycode domains, wildcard URL hosts).

## Researcher access

Researcher participation (`program_researchers`) is a third authorization domain, distinct from both organization membership and program management, and never merged with either: an authorized researcher gains no organization access and no access to any other program by participating in one. Access is invitation-only in this slice — a program manager (organization Owner/Security Admin, or a `program_members` row) invites a specific researcher by email, mirroring the organization-invitation mechanism exactly (hashed, expiring, single-use, email-bound token). Application and public self-enrollment are real, deferred capabilities, not oversights — both require program-visibility concepts (`DOMAIN.md`'s public/private/invite-only/vulnerability-disclosure distinction) that no code branches on yet; see `docs/decisions/0007-researcher-access.md`.

Participation states are `ACTIVE`, `SUSPENDED`, and `REVOKED` — no `PENDING`/`INVITED` state on the participation row, for the identical reason organization membership has none: the pending phase is entirely a `program_invitations` row, and accepting is the transition that creates (or reactivates) the participation at `ACTIVE`. `REVOKED` is not terminal in the sense of being unrecoverable, but it is only ever reversed by a fresh invitation cycle, never by a "reinstate" action, which moves only `SUSPENDED → ACTIVE`.

An active researcher may read the program they participate in and its currently-active scope only — never removed scope history (manager-only, for audit) and never other researchers' identities or participation records (manager-only). Researcher invitation is not gated by program lifecycle status in this slice, unlike scope mutation, because no status-transition RPC exists yet — every program that can currently exist is `DRAFT`, so gating on anything else would make the entire capability unreachable through the product's own flow.

## Reports

Reports preserve researcher-supplied technical content faithfully and can include title, classification, affected asset, description, impact, reproduction steps, evidence, severity/CVSS, status, comments, events, bounty, and resolution.

Primary lifecycle states are `NEW`, `TRIAGING`, `NEEDS_INFORMATION`, `ACCEPTED`, and `RESOLVED`. Alternative terminal outcomes are `DUPLICATE`, `INFORMATIVE`, `NOT_APPLICABLE`, and `REJECTED`.

Legal transitions will be explicit in the report-state service. Researchers cannot change report state. Initial intended transitions are:

```text
NEW → TRIAGING | NEEDS_INFORMATION | ACCEPTED | DUPLICATE | INFORMATIVE | NOT_APPLICABLE | REJECTED
TRIAGING → NEEDS_INFORMATION | ACCEPTED | DUPLICATE | INFORMATIVE | NOT_APPLICABLE | REJECTED
NEEDS_INFORMATION → TRIAGING | ACCEPTED | DUPLICATE | INFORMATIVE | NOT_APPLICABLE | REJECTED
ACCEPTED → RESOLVED | NEEDS_INFORMATION
```

Terminal outcomes have no arbitrary exit transition. Every transition needs an actor and event record.

Submission, triage transitions, communication, evidence (text/code/URL/log and binary file), and final resolution are all implemented. A report is created directly at `NEW` by `submit_report`, which composes three independently-authorized facts — the submitter is an active, authorized researcher for the program (`private.is_researcher_authorized_for_program`), the program currently accepts submissions (blocked only while `PAUSED`/`CLOSED`), and the target is actually in scope (`private.match_program_scope`, the same matching primitive `evaluate_program_scope` uses, factored out specifically so this composition works without one authorization gate leaking into the other) — never reimplementing any of them. The scope decision is frozen at submission time (`matched_scope_entry_id`, `matched_scope_state`, `matched_target`): a report accepted while a target was in scope remains a fully explainable historical record even after that scope entry is later edited or removed, since nothing re-evaluates it after creation. Reports are private by default: visible only to the submitting researcher, an organization Owner/Security Admin, or a `program_members` manager of that program — never another researcher, and never an organization member without program-management standing. See `docs/decisions/0008-report-authorization-and-scope-snapshot.md`.

A report's creation also durably records, in the same transaction as the report row itself, a fact a future asynchronous process may react to (`outbox_events`, a `report.created` event) — infrastructure for the eventual Notifications domain named above, not Notifications itself: no email, webhook, or other real side effect is sent by this event yet. See `docs/decisions/0015-outbox-event-foundation.md`.

## Reputation and financial integrity

Reputation is derived from meaningful platform events, not raw activity, and not from a mutable score column: an append-only `reputation_ledger` records objectively-attributable facts (a report reaching a terminal outcome, a bounty being finalized), each re-derived from the authoritative report/decision row rather than trusted from any event payload, with no scoring formula invented yet — see below. Its eventual scoring algorithm must still resist spam, duplicates, gaming, collusion, and low-quality mass submissions; the ledger's provenance (which organization, which program, which report) is what a future algorithm will need to do that, not a mechanism this foundation already claims to solve. Bounty decision, financial transaction, researcher balance, and payout remain separate concepts, never one mutable browser-controlled value. A report's confirmed severity becomes fixed once it reaches a terminal state (`RESOLVED`, `DUPLICATE`, `INFORMATIVE`, `NOT_APPLICABLE`, `REJECTED`) — a future bounty/payout decision must be able to read it as a stable fact, not a value that can still change after the decision it informed was made. See `docs/decisions/0012-report-resolution-and-classification.md`.

The bounty decision engine is implemented: a program's bounty policy (integer minor units per severity tier, an explicit ISO-shaped currency, never a floating-point amount) is versioned and never edited in place, only ever superseded, so a later policy change can never retroactively alter a report's already-calculated or already-finalized bounty decision. A bounty is not a property of the report row — it is a separate decision (`report_bounty_decisions`) derived from the report's frozen `confirmed_severity` and terminal `status`, the program's *effective policy version at calculation time*, and an explicit organization decision. Only a `RESOLVED` report is bounty-eligible; every other terminal status is a permanent, stored `ineligible` fact, never silently eligible merely because a severity happens to be set. Calculating a recommendation and finalizing a bounty are two different, separately-authorized operations — calculating is triage-shaped authorization, finalizing (and adjusting an already-finalized amount) is restricted to an organization Owner/Security Admin, since committing an actual financial figure is a materially more sensitive act than triage. Reputation, real payment processing, payouts, negotiation, and disputes remain deferred. See `docs/decisions/0013-bounty-decision-engine.md`.

A finalized bounty decision is still not itself a payment: `payment_obligations` (a financial snapshot copied exactly once from a finalized bounty decision — never recalculated, never re-reading the current bounty policy) and `payment_attempts` (that obligation's payout attempt history) are two further, separate concepts, matching this section's own "bounty decision, financial transaction, ... payout remain separate concepts" statement exactly. A finalized decision may produce at most one payment obligation, enforced as a real database constraint. Creating an obligation, initiating a payout attempt, retrying a failed one, and cancelling an obligation are all restricted to an organization Owner/Security Admin — the identical authority that finalizes bounties, since committing to or initiating an actual payout is at least as sensitive. A payout is orchestrated behind a provider-neutral adapter; only a manual (operator-confirmed) provider exists so far, and it never claims a payout succeeded until an authorized actor explicitly records that outcome. Real payment provider integration, payouts to a real account, provider webhooks, and reconciliation remain deferred. See `docs/decisions/0014-payment-ledger-and-payout-orchestration.md`.

Six terminal report/bounty outcomes (`report_resolved`, `report_duplicate`, `report_informative`, `report_not_applicable`, `report_rejected`, `bounty_finalized`) each durably record a reputation fact — via the same `outbox_events` mechanism the report-creation event above uses, consumed by a dedicated `workers/outbox/handlers/reputation/` handler set, with no second queue. The ledger is genuinely append-only (a database trigger rejects any `UPDATE`/`DELETE`, even from a service-role connection), idempotent under both sequential redelivery and genuine concurrent duplicate delivery, and exposes a self-only, aggregate-count read (`get_my_reputation_summary`) — never a raw row, another researcher's facts, or another organization's private detail. A correction mechanism is reserved on the schema (`compensates_fact_id`) but unpopulated, since the domain has no report-reopening mechanism yet to drive one. See `docs/decisions/0016-reputation-ledger-foundation.md`.

A real, public reputation score, a public leaderboard, and a public researcher profile were added on top of this unchanged ledger — see `docs/decisions/0065-reputation-scoring-leaderboard-and-public-profile.md`, which formally supersedes 0016's own "no score, ranking, badge, or leaderboard exists" clause and 0038/0039/0049's prior rejection of a public profile/directory, in response to an explicit researcher-growth requirement. The score (`get_researcher_reputation_score`) is computed read-side from `reputation_ledger` aggregates — `(resolved × 25) + (bounty_finalized × 10) − (rejected × 5)`, with duplicate/informative/not_applicable weighted zero — and is never stored as a mutable column; the ledger itself is untouched by this addition. A researcher who sets a real, chosen, collision-checked `public_username` (`set_my_public_username`) gets a public profile page composing their display name, biography, stated focus areas, and this score — external platform handles, personal details, KYC, and payout information remain excluded from any public surface, unchanged from 0051's original self-only/public-read split.

## Notifications

Notifications are routed and delivered, never embedded in domain RPCs: `report.created`, every terminal report outcome, and `bounty_finalized` each already durably record an outbox event (see above); a dedicated router (`route_and_create_notifications`) re-derives eligible recipients from the exact same authorization predicate the underlying report's own access rules already express — never a second, divergent "who should be notified" rule — checks each recipient's preference, and records a content-free fact (who, what, when) that a separate delivery step later turns into an email. No report title, description, or bounty amount is ever copied onto a notification row; rendering content always goes back through the authoritative, currently-enforced authorization boundary, so a recipient who later loses access to a report also loses the ability to see anything about it beyond "you were notified."

Two notification categories exist: `report_activity` (optional; new-report activity for the organization side, and a researcher's own report reaching a terminal outcome) and `bounty_activity` (mandatory; a bounty being finalized for the researcher's own report — treated like a payment receipt, not a promotional message, and enforced as non-optional by the preference RPC itself, not a UI convention). A recipient who was eligible when a notification was created remains its recipient permanently (a historical fact, never re-resolved), but the actual email content is re-verified for authorization immediately before it is ever rendered — a recipient who loses access between notification creation and delivery receives no content at all, only a permanently-failed delivery record. Email delivery goes through a provider-neutral adapter (`lib/email-provider.ts`); only a development provider is wired up so far, which explicitly logs a simulated delivery and never claims a real send succeeded. Real provider integration, Slack/Teams/push/SMS channels, a digest engine, and researcher-access-change notifications (invitations, suspensions) remain deferred. See `docs/decisions/0017-notification-routing-and-delivery-foundation.md`.

## 10× product principle

Unpatched is not intended to reproduce incumbent workflows. For each major feature ask whether it is materially faster, clearer, safer, easier, more transparent, or more economical; do not make unverified 10× claims.

Report submission should guide scope understanding, asset identification, vulnerability explanation, evidence, validation, and truthful feedback—not merely expose a large form. Triage should prioritize severity, asset, researcher history, duplicate signals, evidence, and required action without unnecessary navigation. Organization views should answer what needs attention, what is risky, blocked, changed, or awaiting a decision rather than decorating empty analytics.
